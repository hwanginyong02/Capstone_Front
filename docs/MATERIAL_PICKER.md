# 재료 고르기와 입력 흐름 개편

2026-10-15 디자인 세션에서 정한 것. 기준 코드는 dev 브랜치(f04eae0, PR #53 머지 시점)와 docs/COMPOSER_COMPONENTS.md, 재료 레지스트리(src/data/reportComposer.ts)다.

참고 파일: `docs/imports/material-picker-prototype.dc.html` — 재료 고르기 프로토타입 소스. 새로 디자인한 것은 **작업 유형과 재료 고르기 두 화면뿐**이다. 프로토타입 안의 재료 입력·확인과 생성 화면은 흐름을 눌러 보기 위한 임시 화면이라 구현 대상이 아니다(5절). 프로토타입 안의 `data()`는 카드·필드·한국어 이름·설명 문구의 초안이고, `renderVals()`는 저장 규칙(7절)의 동작 예시다.

## 1. 전체 흐름

작업 유형 → 재료 고르기 → 재료 입력(카드 순서대로) → 확인과 생성

- 재료 고르기는 성적서 구성 화면(/app/composer)을 대신한다.
- 입력 순서는 사용자가 정하지 않는다. 카탈로그 순서가 곧 입력 순서다. *(§11로 대체됨 — 입력 순서는 사용자가 다이어그램에서 정한다. 카탈로그 순서는 처음 순서다)*
- "평가만 하고 끝내는" 동선은 없다.

## 2. 카드 구조 — 9장을 대분류 4개로 묶는다

| 대분류 | 카드 (레지스트리 id) | 구분 |
|---|---|---|
| 의뢰 정보 | 의뢰자 정보 ③ (clientInfo) | 필수 |
| 모델 | 평가 대상 모델 ④ (model) | 필수 |
| 모델 | 모델 설정과 실행 환경 ⑨ (modelEnv) | 선택 카드 |
| 데이터 | 평가 데이터 ① (evalData) | 필수 |
| 데이터 | 학습 데이터 ⑥ (trainingData) | 선택 카드 |
| 데이터 | 테스트 데이터 ⑦ (testData) | 선택 카드 |
| 데이터 | 정답 라벨 ⑧ (groundTruth) | 선택 카드 |
| 평가 기준 | 평가 관점 ⑤ (perspective) | 필수 |
| 평가 기준 | 지표와 합격 기준 ② (metrics) | 필수 |

카드 안의 필드는 레지스트리를 그대로 따른다.

## 3. 입력 순서 — 카드 순서로 바꾼다

의뢰자 정보 → 평가 대상 모델 → (모델 설정과 실행 환경) → 평가 데이터(업로드, 컬럼 매핑) → (학습 데이터) → (테스트 데이터) → (정답 라벨) → 평가 관점 → 지표와 합격 기준 → 검증 → 확인과 생성

*(§11로 대체됨 — 위 순서는 처음 순서다. 사용자가 레인과 카드 순서를 바꿀 수 있고, "지표와 합격 기준·학습 데이터는 평가 데이터 뒤"라는 규칙만 지킨다. 검증과 확인과 생성은 늘 맨 끝이다)*

- 지금은 "백엔드가 지표 목록 없이 검증·평가 요청을 받지 않는다"는 이유로 파일 → 지표 → 매핑 → 검증이 앞에 있다(WORKFLOW_REDESIGN §2.1, §11). 이 순서를 버리므로 다음을 함께 바꾼다.
  - 컬럼 매핑이 지표에 기대지 않게 한다. 매핑을 먼저 하고, 지표 화면에서 매핑된 컬럼으로 계산할 수 없는 지표(예: 확률 컬럼 없이 AUROC, AUPRC, Log Loss)는 처음부터 비활성으로 두고 이유를 한 줄 붙인다. "지표 제외" 처리는 없앤다.
  - 검증은 지표와 합격 기준 뒤, 확인과 생성 앞으로 옮긴다. 백엔드는 바꾸지 않는다.
  - 평가 관점은 지표 바로 앞이다. 지표 화면이 이 답으로 "목적별 점검"(재료 선택 점검 3층)을 보여 주고, "추천 지표"는 유형별 기본 세트에 맞지 않는 줄의 추천 지표를 더한다(이진에서 불균형 비율이 9를 넘으면 AUPRC). 같은 점검을 검증 화면 "다음"에서 다시 하고, 경고를 보고 진행한 기록이 성적서 6.0에 남는다(`src/lib/report/materialCheck.ts`).
- 합격 목표값은 지표와 합격 기준에서 평가 전에 받는다. 결과와의 비교는 성적서에서 확인한다.
- 학습 데이터의 클래스별 데이터 양은 평가 데이터의 클래스 목록이 필요하다. 평가 데이터가 앞이라 지켜진다.

## 4. 재료 고르기 화면 구조 (3단)

- 왼쪽: 대분류 네모 카드 4개. 고르면 그 아래에 카드 목록이 나온다. 목록은 테두리 하나 안에 두고 줄마다 구분선을 긋는다. 필수 카드에는 "필수"라는 글자를 붙인다.
- 가운데: 고른 카드의 필드. 섹션은 필수 / 권장 / 선택 / 조건부. 필수는 체크박스 없이 글자만, 권장과 선택은 체크박스(기본 꺼짐), 조건부는 조건 문구와 함께 보여준다. 아래에 저장 버튼.
- 오른쪽: 입력 순서. 필수 카드와, 항목을 하나 이상 골라 저장한 선택 카드가 순서대로 나온다. 라벨 없음. 아래에 "필수 5개 중 N개 저장"과 이전/다음.

*(§11로 대체됨 — 왼쪽 재료 목록(대분류 → 카드 → 항목 나무), 가운데 4열 다이어그램, 하단 현황 바다. 대분류 네모 카드·오른쪽 입력 순서 패널·저장 버튼은 없앴다)*

## 5. 재료 입력 화면 — 기존 화면을 쓴다

재료 입력과 확인과 생성은 새로 디자인하지 않는다. 지금 있는 화면을 쓰고, 세 가지만 바꾼다.

1. 디자인 시스템(10절)과 한국어 문구(8절)를 입힌다.
2. 재료 고르기에서 체크하지 않은 권장·선택 필드는 숨긴다. 필수 필드는 늘 보인다.
3. 화면 순서를 3절의 카드 순서로 바꾼다.

| 카드 | 지금 화면 (파일) | 지금 그 화면이 받는 것 | 바꿀 것 |
|---|---|---|---|
| 의뢰자 정보 ③ | Details (/report/:id/issue-info, pages/report/ReportInfo.tsx) | ③ 전체, ④ 모델 용도, ② 합격 기준·핵심 지표 | ③만 남기고 ④·②는 각자 카드 화면으로 옮긴다 |
| 평가 대상 모델 ④ | 업로드 화면(모델명·버전)과 Details(모델 용도)에 나뉘어 있음 | — | 한 화면으로 모은다 |
| 모델 설정과 실행 환경 ⑨ | Model info (/report/:id/model-env, pages/report/ModelEnv.tsx) | ⑨ 전체 | 순서만 앞으로 |
| 평가 데이터 ① | Evaluation File (pages/DataUpload.tsx) + Column mapping (pages/ColumnMapping.tsx) | 파일, 매핑, 양성 클래스, 결정 임계값 | 매핑이 지표에 기대지 않게(3절) |
| 학습·테스트 데이터, 정답 라벨 ⑥⑦⑧ | Data info (/report/:id/data-info, pages/report/DataInfo.tsx) | 켠 카드만 카드 순서대로 | 그대로 *(§11로 대체됨 — 카드마다 한 단계: /app/training-data, /app/test-data, /app/ground-truth)* |
| 평가 관점 ⑤ | Metrics 화면 맨 위 (pages/TestItems.tsx) | ⑤ 전체 | 지표 바로 앞 단계로 |
| 지표와 합격 기준 ② | Metrics (지표, β, 선택 이유) + Details의 합격 기준 표 | — | 합격 기준 표를 지표 쪽으로 합치고, 계산할 수 없는 지표는 비활성 |
| (검증) | Validation (pages/DataValidation.tsx) | 검증, 재료 선택 점검(생성 전 안내), run 저장 | 지표와 합격 기준 뒤로. "다음"에서 1층 빈칸은 막고 2·3층 경고는 기록 |
| 확인과 생성 | Result (/report/:id) | 평가 실행, AI 서술, 성적서 | 빠진 재료 안내는 검증 화면으로 옮겼다(생성 전 안내). 성적서는 표지·1.4·6.0 에 점검 결과를 찍는다 |

- Details, Data info, Model info는 지금 run id가 있어야 열리는 경로(/report/:runId/...)다(src/data/workflowSteps.ts의 runScoped). run은 검증에서 만들어지고, 이 화면들이 검증보다 앞으로 오므로 /app/* 경로로 옮긴다. 값은 지금처럼 워크플로 저장소에 둔다.

## 6. 표준 보고 항목 규칙 — 항목별 체크, 기본 꺼짐

- 지금은 "선택 카드를 켜면 그 안의 표준 보고 항목은 필수, 모르면 모름"이다(COMPOSER_COMPONENTS "결정 사항과 열린 결정"). 이것을 바꾼다.
- 선택 카드(⑥~⑨) 안의 표준 보고 항목(레지스트리의 required)은 "권장"으로 보여주고 항목마다 체크한다. 기본은 꺼짐. 끈 항목은 성적서에 "제공되지 않음"으로 찍히고, 검증 화면의 생성 전 안내(재료 선택 점검 2층)가 알린다.
- 권장 항목은 재료 한 줄 단위로 묶어 체크한다(예: 실행 환경의 OS, CPU, GPU, 메모리, 소프트웨어). 선택 항목은 하나씩 체크한다.
- 체크해서 받기로 한 권장 항목은 입력 화면에서 비울 수 없고, 모르면 "모름"을 고른다(지금 규칙과 같다).

## 7. 저장 규칙 (재료 고르기)

*(§11로 대체됨 — 저장 단계는 없다. 넣고 빼는 즉시 반영되고, 필수 카드는 처음부터 들어가 있어 다음을 막지 않는다. 아래는 종전 기록)*

- 저장 = 그 카드에서 무엇을 받을지(체크 상태)를 확정하는 것. 실제 값 입력이 아니다.
- 저장하면 카드 줄과 오른쪽 입력 순서의 카드가 저장 표시(강조 배경 + 체크)로 바뀐다. 대분류 안의 필수 카드가 모두 저장되면 대분류 카드도 저장 표시로 바뀐다.
- 필수 카드를 하나라도 저장하지 않고 다음을 누르면 넘어가지 않고, 저장하지 않은 필수 카드 이름을 오류로 보여준다.
- 선택 카드를 저장하지 않으면 그 카드는 빼고 진행한다. 아무것도 체크하지 않고 저장한 선택 카드는 "넣지 않기로 확정"이다.
- 저장하지 않고 다른 카드로 가도 체크는 화면에 남지만 반영되지 않는다. 다음을 누르면 마지막으로 저장한 내용이 적용된다. 저장한 뒤 체크를 바꾸면 "저장하지 않은 변경이 있어요"를 보여준다.

## 8. 필드 표시와 문구

- 재료 고르기에서 필드는 하나씩 쪼개 보여준다(예: 회사명, 대표자, 사업자등록번호를 따로).
- 필드 이름은 검정, 그 필드만의 짧은 설명은 회색, 형식(텍스트, CSV/JSON 파일, 하나 선택 등)은 이름 오른쪽에 회색으로.
- 필드 설명 문구는 초안이다(프로토타입 `data()`의 desc). 검토가 필요하다.
- **앱 화면 문구를 전부 한국어로 바꾼다.** 지금은 기존 테스트가 영문 문자열을 찾고 있어 영어로 통일해 두었다(WORKFLOW_REDESIGN §6.3). 바꿀 때 테스트도 함께 고친다.
- 선택지 **저장값은 영어 그대로 둔다.** 화면에 보이는 이름만 한국어로 바꾼다. 성적서에 찍히는 이름은 지금처럼 reportLabels를 쓴다. 저장된 데이터를 옮기지 않는다.

## 11. 다이어그램으로 고르고 순서 정하기 (2026-10-16 팀 피드백 반영)

PR #54 이후 팀 피드백: 화면이 각 필드 설명을 보여 주는 데 그치고, 사용자가 직접 구성하며 상태를 확인하는 흐름이 아니었다. 다이어그램이 오른쪽에 작게 있었고, 순서를 바꿀 수 없었으며, 필수 카드까지 저장을 눌러야 반영됐다. 아래가 그 결정이다. §1·§3·§4·§7의 해당 부분을 대체한다.

### 11.1 화면 구조

- **왼쪽 재료 목록**: 대분류와 그 안의 카드(서브 카탈로그)만 둔다. 대분류마다 연한 회색 테두리 상자로 묶고, 머리는 회색 띠, 카드 줄 사이는 구분선이다. 대분류에 "카드 n장" 같은 수 문구는 달지 않는다. 카드를 누르면 가운데 아래 필드 패널에 그 카드가 열린다(고른 카드는 강조 배경과 왼쪽 강조 막대). 넣지 않은 선택 카드는 ＋나 끌어 놓기로 넣는다.
- **가운데 아래 필드 패널**: 고른 카드의 필드가 필수 / 권장 / 선택 / 조건부로 나뉘어 두 줄 격자로 나온다. 머리(카드 이름·카드 넣기)는 그대로 두고 **필드만 패널 안에서 스크롤한다** — 페이지를 내리지 않고 바로 위 다이어그램으로 끌어 놓는다(다이어그램 옆에 두는 3단 배치도 해 봤지만 오히려 불편해 되돌렸다).
- **페이지 스크롤 없음**: 데스크톱(lg 이상)에서는 브라우저 전체 스크롤을 만들지 않는다(셸의 `fitViewport`). 위 헤더와 아래 하단 바 사이의 높이를 영역끼리 나누고, 넘치는 것은 각자 안에서 스크롤한다 — 재료 목록, 다이어그램(가운데 높이의 최대 55%), 필드 패널(남은 높이 전부, 필드 목록만 스크롤). 좁은 화면은 영역을 한 화면에 담을 수 없어 페이지가 스크롤하고, 필드 목록은 최소 360px·화면 높이의 45%로 둔다. 필드마다 이름(검정), 입력 형식(오른쪽 회색), 조건, 설명(회색)을 **마우스를 올리지 않아도** 그대로 보인다(§8과 같은 표시). 권장 필드는 그 안의 칸(운영체제·CPU·…)을 아래에 나열한다. 권장·선택 칸은 위 다이어그램으로 끌어 놓거나 ＋로 넣는다. 필수·조건부는 늘 들어가므로 버튼이 없다. 넣지 않은 선택 카드는 머리의 "카드 넣기"로 통째로 넣는다. 왼쪽이 좁아 필드를 다 담지 못하고 다이어그램 아래가 비어 있어 여기에 둔다.
- **구분 색**: 색은 구분 하나에만 쓴다 — 필수 네이비(강조색), 권장 앰버(주의색), 선택·조건부 회색. 필드 패널의 구분 머리(진한 배경에 흰 글자, 조건부만 연한 회색 — 옆에 설명 글은 두지 않는다)와 칸 왼쪽 띠, 다이어그램 칩의 점, 하단 현황의 점이 같은 색이다(`kindStyles.ts`). 권장이 앰버인 것은 빠지면 하단 바가 같은 색으로 경고하기 때문이다. 조건부 칸은 점선 테두리다. 형식은 이름 옆 작은 칩이고, "하나 선택: …"의 선택지는 칩 아래 줄에 적는다. 설명 끝의 "예: …"는 한 줄 떼어 연하게 보인다. 파일을 받는 필드(① 결과 파일)는 두 칸 폭으로 넓히고, 이 분류 유형의 파일 예시를 업로드 화면과 같은 표(`CsvExampleViewer`)와 필수 컬럼 안내로 붙인다.
- **가운데 다이어그램**: 대분류 4열 레인이다. 레인 사이는 **화살표(→)**로 대분류 순서를 보인다. 레인 안은 화살표 없이 **세로축**을 따라 위에서 아래로 읽는다 — 카드 왼쪽 세로축 위에 입력 순서 번호가 있고, 같은 레인의 다음 번호까지 선으로 잇는다. 노드에는 카드 이름과 받기로 고른 권장·선택 항목의 칩만 붙는다 — "필수 n"이나 "권장 x/y" 같은 숫자는 두지 않는다(필수는 늘 들어가고, 현황 숫자는 하단 바에 있다). 칩은 ×로 뺀다. 노드를 누르면 그 카드가 필드 패널에 열리고(패널이 화면 밖이면 스크롤), 열린 노드는 강조 테두리로 보인다. 필드 설명은 한 곳(필드 패널)에서만 읽는다.
- **하단 바**: 필수 카드 수, 권장 들어간 수/전체, 선택 들어간 수/전체, 품질 단계, 그리고 표준까지 남은 권장 항목 경고. "빠진 항목 보기"로 펼쳐 바로 넣는다. 이전·다음도 여기 있다.
- **추천 세트**: 머리 오른쪽의 최소 / 표준 / 상세. 적용하면 항목을 통째로 바꾸고 "되돌리기"를 보인다. 지금 고른 것이 세트와 똑같을 때만 그 버튼이 눌린 모양이다.

코드: `pages/MaterialPicker.tsx`, `components/material-picker/`(`PickPalette`, `PickDiagram`, `DiagramLane`, `CardNode`, `FieldPanel`, `PickStatusBar`, `PickSetToggle`, `dnd.ts`).

### 11.2 넣고 빼기 — 바로 반영

- 저장 단계는 없다. 넣고 빼는 즉시 스토어(`materialPicks`)에 들어가고 다이어그램에 보인다.
- (대체됨 2026-10-18, §12.2) 필수 카드와 그 안의 필수·조건부 필드는 처음부터 들어가 있었다. 재료 고르기에 들어오면 필수 카드의 키를 빈 배열로 채웠다(`initRequiredPicks`, 삭제됨).
- 선택 카드를 끌어 놓거나 ＋를 누르면 그 카드의 **권장 항목이 모두 든 채로** 들어간다. 카드를 싣겠다는 뜻이므로 표준 보고 항목을 빠짐없이 받는 쪽을 기본으로 둔다. 권장이 없는 카드면 선택 항목이 모두 든다.
- 항목을 끌어 놓거나 ＋를 누르면 그 항목이 원래 카드에 들어가고, 카드가 빠져 있었으면 카드도 들어간다.
- 선택 카드는 항목이 하나라도 있으면 들어간 것이다(§7 규칙 유지). 마지막 칩을 빼거나 노드의 ×를 누르거나 노드를 재료 목록으로 끌어 오면 빠진다.
- 새로 들어간 선택 카드는 그 레인 맨 아래로 간다.

### 11.3 입력 순서

- 순서 = **레인 순서 + 레인 안 카드 순서**다. 왼쪽 레인부터, 레인 안에서는 위부터 읽은 것이 입력 순서다. 대분류끼리는 섞이지 않는다.
- 레인 머리를 좌우로 끌거나 ◀▶, 노드를 위아래로 끌거나 ▲▼로 바꾼다. 모든 끌기에는 같은 일을 하는 버튼이 있다(HTML5 끌어 놓기는 키보드로 할 수 없다).
- 스토어는 평탄한 카드 목록 하나(`cardOrder`)로 든다. 넣지 않은 선택 카드도 자리를 갖는다.
- **깨면 놓지 못하는 규칙**(`ORDER_RULES`). 어기는 자리에 놓으면 원래 자리에 두고 이유를 한 줄로 보인다.
  1. 지표와 합격 기준은 평가 데이터 뒤 — 컬럼 매핑 결과로 계산할 수 있는 지표를 정한다. 레인으로 보면 '평가 기준' 레인은 '데이터' 레인 뒤에만 온다.
  2. 학습 데이터는 평가 데이터 뒤 — 클래스별 데이터 양을 평가 데이터의 클래스 목록으로 받는다.
- (대체됨 2026-10-18, §12.2) ~~알리기만 하는 권고(`ORDER_HINTS`)~~ — 평가 관점 → 지표는 이제 깨면 놓지 못하는 규칙이다.
- 검증과 확인과 생성은 카드가 아니라 순서와 무관하게 늘 맨 끝이다.
- 단계 목록은 들어간 카드를 이 순서대로 카드의 `steps` 로 펼친 것이다(`buildStepList(selection, order)`). ① 평가 데이터는 업로드와 컬럼 매핑 두 단계가 된다.

### 11.4 데이터 카드 단계 분리

- ⑥ ⑦ ⑧ 을 묶던 "데이터 정보" 단계를 카드마다 한 단계로 나눴다(`/app/training-data`, `/app/test-data`, `/app/ground-truth`). 사용자 순서에서는 셋이 떨어질 수 있다(예: 테스트 데이터 → 평가 데이터 → 학습 데이터).
- 단계 수는 최소 8, 전체 12다.
- `/app/data-info` 옛 링크는 넣은 첫 데이터 카드의 단계로, 없으면 재료 고르기로 보낸다.
- persist v13: `cardOrder` 를 카탈로그 순서로 채우고, 진행 표시의 `"dataInfo"` 는 넣어 둔 데이터 카드 단계로 옮긴다.

### 11.5 품질 단계와 추천 세트

| 단계 | 받는 것 | 성적서 |
|---|---|---|
| 최소 | 필수만 | 나온다. 표준 보고 항목(권장)이 "제공되지 않음"으로 찍힌다 |
| 표준 | 최소 + 모든 선택 카드의 권장 항목 전부 | **충분한 품질의 기준선.** 표준 보고 항목을 모두 갖춘다 |
| 상세 | 표준 + 모든 선택 항목 | AI 서술이 기댈 근거가 가장 많다 |

- 지금 단계는 고른 것에서 계산한다(`pickTier`): 권장을 다 받으면 표준, 선택까지 다 받으면 상세, 그 밖은 최소.
- 하단 바는 표준에 못 미치면 "표준까지 권장 k개"와 "제공되지 않음" 경고를 보인다.
- 받기로 한 권장 항목은 입력 화면에서 비울 수 없고 모르면 "모름"을 고른다(§6 그대로).

### 11.6 단계 표시줄

- 입력 화면의 단계 표시줄 맨 위에 "재료 고르기" 버튼을 둔다. 순서와 넣을 항목을 언제든 다이어그램에서 다시 본다.
- 첫 단계의 이전은 재료 고르기로 간다. 첫 단계가 순서에 따라 달라지므로 화면이 아니라 `useStepFlow` 가 정한다.

## 12. 평가 흐름 만들기 (2026-10-18 개편)

재료 고르기 화면을 **평가 흐름 만들기**로 바꾼다. 빈 흐름도에서 시작해 왼쪽 트리의 항목을 단계에 넣으면 블록이 생기고, 필수 항목을 모두 넣어야 "다음"으로 간다. 함께 정한 것: 입력 재료 목록 중 레지스트리 밖에서 받던 재료(매핑 컬럼·양성 클래스·결정 임계값·모델 분류·예시 파일 등)도 트리 항목으로 넣어, "넣지 않으면 받지 않는다" 규칙을 모든 입력에 맞춘다.

하위 절은 작업 순서대로 채운다: 12.1 레지스트리, 12.2 흐름 규칙과 저장 이행(v15), 12.3 화면·용어·표준 근거, 12.4 매핑, 12.5 모름과 입력 점검. 아직 비어 있는 절은 해당 작업이 끝나면 적는다.

### 12.1 레지스트리 — 항목, 표시, 개수

**항목 단위.** 평가 흐름에서 넣고 빼는 단위(항목)는 필드다. '회사 정보' 하나에 다섯 칸이 들어 있고, 칸 목록은 설명 팝업이 보인다. 고를 수 있는 선택 칸(홈페이지·팩스)만 칸마다 항목이다(`contactExtra:website`). 조건부 필드는 항목이 아니다 — 조건을 정하는 항목을 넣으면 함께 들어간다.

**새 항목 10개.** 입력은 지금 화면이 그대로 받는다(아래 `dedicatedScreen`). 레지스트리에 들어와 트리·팝업·개수에 나타난다.

| 블록 | 항목 | 구분 | 받는 화면 |
|---|---|---|---|
| ① 평가 데이터 | 정답 컬럼 (y_true) | 필수 | 컬럼 매핑 |
| | 예측 컬럼 (y_pred·score·prob_class_*·prob_label_* 중 하나 이상) | 필수 | 컬럼 매핑 |
| | 양성 클래스 | 필수, 이진만 | 컬럼 매핑 |
| | 결정 임계값 | 예측 컬럼과 함께 들어감, 이진·멀티레이블 | 컬럼 매핑 |
| | 지연시간 컬럼 (latency) | 권장 (2층 8번) | 컬럼 매핑 |
| | 샘플 ID 컬럼 (id) | 선택 | 컬럼 매핑 |
| | 클래스 레이블 설명 | 선택 | 컬럼 매핑 |
| ④ 평가 대상 모델 | 모델 분류 | 필수 | 평가 대상 모델 |
| ⑥ 학습 데이터 | 적합 예시 파일 | 선택 | 학습 데이터 |
| | 부적합 예시 파일 | 선택 | 학습 데이터 |

남는 컬럼을 치우는 '쓰지 않음(ignore)'은 재료가 아니라 항목에 넣지 않는다.

**바뀐 필드.**
- 평가 의뢰일: 선택 → **필수**. 1층 검사가 늘 요구하는데 선택이라 칸이 숨을 수 있었다. 의뢰자 정보 화면에 늘 보인다.
- 성적서 용도: 레지스트리의 저장값을 실제 저장값 `internal / external / project` 로 맞췄다(종전 영어 문장은 어디에도 저장되지 않아 과제 정보의 조건이 성립할 수 없었다). 덧붙이는 글(`allowsNote`)과 선택지 설명을 레지스트리에 두고, 화면의 라디오가 이것을 읽는다.
- ⑧ 정답 라벨 신뢰성(종전 '라벨 검수 방식'): 선택지 이름을 성적서 표기와 같은 '복수 라벨러 합의 / 단일 라벨러 / 검토 없음'으로 바꿨다. 저장값은 그대로다.

**필드 표시.**

| 표시 | 뜻 |
|---|---|
| `dedicatedScreen` | 레지스트리 폼이 아니라 전용 화면(업로드·매핑·지표·③④ 폼·예시 파일 칸)이 받는다. 레지스트리 폼은 그리지 않고 필드 점검도 건너뛴다. 파일·지표·컬럼 입력과 칸이 나뉜 필드는 모두 이 표시가 있다. |
| `conditionField` | 조건을 값으로 읽을 수 없는 조건부 필드의 트리거(β ← 지표, 결정 임계값 ← 예측 컬럼). 값으로 읽을 수 있으면 `requiredWhen` 에 적고, 둘을 함께 적지 않는다. |
| `columnRoles` | 컬럼 항목이 받는 매핑 역할. 유형마다 매핑할 수 있는 역할은 정확히 한 항목이 맡는다. |
| `standardBasis` | 표준 근거 `{standard, clause, requirement?, reportingItem?}`. 1층 식별 항목은 ISO/IEC 17025 7.8.2.1 e)·g), 권장 항목과 평가 관점은 TS 4213 조항이다. `reportingItem` 은 재료 선택 점검 2층 번호(성적서가 "제공되지 않음"을 세는 번호)와 같다. 요구 문장은 표준 원문과 대조한 것만 적는다(지금은 없음). |
| `maxLength` | 글 칸의 글자 수 상한(아래). |

**조건부 항목과 조건을 정하는 항목** (`conditionTriggerIds` 한 곳에서 읽는다).

| 조건부 항목 | 조건을 정하는 항목 |
|---|---|
| ① 결정 임계값 | 예측 컬럼 |
| ② β | 지표 |
| ③ 과제 정보 | 성적서 용도 |
| ⑧ 라벨러 수, 일치도 종류 | 정답 라벨 신뢰성 |
| ⑧ 일치도 값 | 정답 라벨 신뢰성, 일치도 종류 |

입력 화면이 조건부 필드를 받는지는 `isFieldReceived` 가 본다 — 조건을 정하는 항목도 받을 때만 받는다(B2). `isFieldPicked` 의 뜻은 바꾸지 않았다.

**구분 유도.** 권장은 두 곳에서 나온다. 선택 카드의 필수 필드(종전과 같음, `pickKind`)와, 잠긴 카드의 선택 필드 중 2층 번호가 있는 것(`leafKind` — 지연시간 컬럼 하나)이다. `pickKind` 는 저장 이행 v12 가 기대므로 바꾸지 않는다.

**항목 수** (조건부 제외. 하단 바와 "다음" 막힘이 세는 수의 정본, `reportComposer.test.ts` 가 고정한다).

| | 이진 | 다중 클래스 | 멀티레이블 |
|---|---|---|---|
| 필수 | 15 | 14 (양성 클래스 없음) | 15 (양성 클래스 없음, 지표 선택 이유 있음) |
| 권장 | 15 | 15 | 15 |
| 선택 | 13 | 13 | 13 |

- 필수 = ③ 회사 정보·성적서 용도·평가 의뢰일 + ④ 모델 이름·버전·용도·분류 + ① 결과 파일·정답 컬럼·예측 컬럼·양성 클래스(이진) + ⑤ 질문 2개 + ② 지표·합격 기준·핵심 지표(멀티레이블은 지표 선택 이유 +1)
- 권장 = ⑨ 4 + ⑥ 6 + ⑦ 2 + ⑧ 2 + ① 지연시간 컬럼
- 선택 = ③ 홈페이지·팩스·과제 번호 + ① 샘플 ID 컬럼·클래스 레이블 설명 + ⑥ 7 + ⑦ 1

**글자 수 상한(B7).** AI 에 넘기는 고객 입력은 백엔드가 직렬화 길이 2만 자로 막고, 넘으면 서술 요청이 통째로 거절되어 성적서에 AI 서술이 하나도 실리지 않는다. 그래서 두 겹으로 막는다.
- 칸마다 상한을 두고 남은 글자를 보인다: 한 줄 글 200자, 모델 용도·분류 100자(1절 문장 안에 끼워 찍힘), 학습 데이터 설명 2,000자, 비고 1,000자, 덧붙이는 글 500자, 기타 직접 입력 200자, 클래스 설명 클래스마다 200자.
- 보내기 직전 `fitClientInputs` 가 길이를 상한의 90%(18,000자)에 맞춘다. 가장 긴 글부터 잘라 "…(이하 생략)"을 붙이고, 그래도 넘으면 클래스 설명을 뺀다. 백엔드는 공백이 든 구분자로 재 프론트보다 길게 세므로 10% 여유가 그 차이를 덮는다.

### 12.2 흐름 규칙과 저장 이행(v15)

**두 가지 물음을 따로 둔다.** 같은 `materialPicks` 를 두 쪽이 다르게 읽는다.

| 묻는 것 | 함수 | picks 에 그 블록 키가 없을 때 | 필수 항목 | 조건부 항목 | 쓰는 곳 |
|---|---|---|---|---|---|
| 입력 화면이 받는가 | `isFieldPicked`·`isPartPicked`, 조건부까지 보면 `isFieldReceived` | 모두 받음 | 늘 받음 | 조건을 정하는 항목을 받을 때 | 입력 화면, 필수 점검, 1층 재확인, 성적서 매퍼 |
| 평가 흐름에 놓였는가 | `isLeafPlaced` | **아무것도 안 놓임** | 넣었을 때만 | 조건을 정하는 항목이 모두 놓였을 때 | 트리, 블록, 하단 바, "다음" |

필수 항목 id 도 `materialPicks` 에 함께 담는다(새 키 없음). 입력 쪽은 필수를 늘 받으므로 영향이 없다. 조건부는 저장하지 않고 조건을 정하는 항목에서 유도한다.

**판정 지점 하나.** 개수·빠진 필수·빠진 권장은 `flowStatus(taskType, picks)` 한 번의 결과다. 화면은 따로 세지 않는다.
- 셈은 지금 유형의 항목만, 조건부를 빼고 센다. 다른 유형의 항목(이진 저장분의 클래스 중요도 등)이 picks 에 있어도 세지 않는다.
- 필수 수는 `전체 − 빠진 필수 수` 로 만든다 — 하단 바 숫자와 막힘 안내가 다를 수 없다.
- 막힘 안내는 `describeMissingRequired` 한 곳: "넣지 않은 필수 항목이 있어요: 회사 정보, 성적서 용도, 평가 의뢰일 외 n개"(카탈로그 순서로 처음 셋).
- 블록이 보이는 것은 이 유형의 (조건부가 아닌) 항목이 하나라도 놓였을 때다(`isBlockShown`).

**넣고 빼기.**
- `togglePlaced`: 넣을 수 없는 id(조건부·모르는 id)는 무시하고, 레지스트리 순서로 둔다. 다른 유형의 항목은 남긴다 — 유형을 바꿨다 돌아와도 다시 넣지 않게.
- 블록째 넣기(`blockFillIds`)는 필수와 권장, 둘 다 없는 블록이면 선택 전부다.
- 필수 항목도, 잠긴 블록 전체도 뺄 수 있다. 다시 "다음"이 막힐 뿐 입력 쪽에는 영향이 없다. 조건을 정하는 항목을 빼면 조건부도 빠진다.
- 키는 사용자가 넣거나 비울 때만 생긴다. 화면에 들어오기만 해서 키를 만들던 `initRequiredPicks` 는 지웠다 — 잠긴 카드의 `[]` 는 "사용자가 비웠다" 하나의 뜻이다.

**블록 순서.**
- 단계 목록·진입 가드·순서 규칙은 지금처럼 잠긴 카드를 늘 포함한다. 흐름도에 아직 놓이지 않은 잠긴 블록도 자리를 지킨다.
- 처음 놓은 블록의 자리는 `orderAfterPlacing` 하나가 정한다: 꺼져 있던 선택 블록은 레인 끝, 잠긴 블록은 제자리. 스토어와 흐름도의 놓을 자리 미리보기가 같은 함수를 쓴다.
- 순서 규칙(`ORDER_RULES`)은 셋이다: 평가 데이터 → 지표, 평가 데이터 → 학습 데이터, **평가 관점 → 지표**. 마지막 것은 종전에 막지 않는 권고였는데, 지표 추천이 관점의 답을 읽으므로 규칙으로 올렸다(D4).

**"다음"이 갈 곳**(`composerNextStep`). 들어올 때 넘겨받은 돌아갈 화면이 목록에 있으면 거기 → 아니면 처음 미완료 입력 화면 → 모두 마쳤으면 검증. 성적서로 가지 않는다. 다른 화면에서 들어올 때 넘기는 값은 `FlowEntryState {cardId, leafIds?, returnStep?}` 이고, 강조할 항목은 `focusLeafIds` 가 정한다(넘긴 항목, 없으면 그 블록의 넣지 않은 필수·권장).

**평가 의뢰일 기본값(B1②).** `DEFAULT_BASIC_INFO` 의 날짜는 비어 있다(모듈을 읽은 날로 굳지 않게). 새 평가 초기화(`resetWorkflow`)가 `createDefaultBasicInfo()` 로 그날 날짜를 넣고, 의뢰자 정보 화면은 저장값이 비었을 때만 오늘을 저장한다. 작업 유형을 바꿔도 고른 날짜는 그대로다.

**저장 이행 v15.** 잠긴 카드 키의 뜻이 "필수는 들어가 있음"에서 "넣은 항목만"으로 바뀌어, 진행 중인 저장분이 "다음"에서 갇히지 않게 종전에 받던 것을 넣은 것으로 옮긴다.

| 저장분 | 처리 |
|---|---|
| 잠긴 카드 키가 있음 | 모든 유형의 필수 항목을 더한다(합집합 — 유형을 바꿔도 다시 넣지 않게) |
| 위 + ① 평가 데이터 | 지연시간 컬럼(종전엔 늘 받음). 매핑에 id 역할이 있으면 샘플 ID 컬럼, 빈칸 아닌 설명이 있으면 클래스 레이블 설명 |
| ⑥ 학습 데이터가 켜져 있음 | 올려 둔 예시 파일의 항목 |
| 키가 없는 카드, 다른 선택 카드 | 그대로 |
| 지표가 평가 관점보다 앞인 순서 | 관점을 지표 바로 앞으로(D4 규칙이 생겨 그대로 두면 모든 순서 이동이 막힘) |

합집합이라 여러 번 돌려도 같다. v11 이하 저장분은 v12 가 잠긴 카드 키를 늘 만들어 두므로 v15 까지 지나면 필수가 채워진다. `placeableIds`·`leafKind` 는 v15 가 부르므로 뜻을 바꾸려면 새 함수를 더한다(v12 의 `pickableIds`·`pickKind` 와 같은 이유).

**설계로 닫은 것.** 하이퍼파라미터의 이름 없는 줄 문제 중 "알고리즘과 하이퍼파라미터를 따로 고를 수 있다"(B6①)는 블록째 넣기가 둘 다 넣으므로 따로 고치지 않았다. 이름·값 중 하나만 적은 줄(B6②)은 입력 점검에서 다룬다.
