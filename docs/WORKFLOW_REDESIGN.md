## 1. 왜 바꾸나

지도교수 피드백(2026-09-19):

> 기능 추가하여 컴포넌트화 하고 여러 워크플로우를 할 수 있도록
> 이진, 멀티클래스, 멀티레이블 각각에 맞는 평가를 한다. UI상으로 아이콘화하여 만들기

이 피드백을 **"세 분류 유형을 각각 독립된 워크플로우로 분리하고, 아이콘으로 고르게 하라"**
로 읽었다. 코드를 보면 두 가지 문제가 겹쳐 있다.

### 1.1 세 유형은 이미 다르게 평가되는데, 화면에 드러나지 않는다

`task_type` 은 노출 지표·요구 컬럼·매핑 가능 역할·임계값 의미·예측 파생 방식을 전부
가른다(`data/evaluationData.ts`). 백엔드도 `metrics/{binary,multiclass,multilabel}` 로
파일이 갈려 있다. **차이는 이미 구현돼 있다.**

그런데 사용자 눈에는 안 보인다. 세 유형이 하나의 공용 화면 안에서 조건문으로만 갈리고,
유형 선택은 `basic-info` 세 번째 카드의 마지막 항목이다
(`components/basic-info/BasicInfo.tsx` — Classifier type). 앱 전체를 가르는 분기점이
폼 필드 하나와 같은 무게로 놓여 있다.

선택한 뒤에도 자기가 무슨 평가 중인지 알 방법이 없다 — `AppHeader` 는 "ML Evaluation"
고정 텍스트고 `StepTabs` 는 숫자 1~7 이다.

**→ 없는 기능을 만드는 게 아니라, 이미 있는 차이를 드러내는 작업이다.**

### 1.2 평가와 발급이 한 흐름에 엉켜 있다

`/api/evaluate` 로 실제로 보내는 payload 전부(`hooks/useReportData.ts`):

```js
{ task_type, column_mappings, selected_metric_ids, metadata, beta, decision_threshold }
```

회사명·대표자·사업자등록번호·전화·주소·계약일 — **하나도 안 들어간다.** 이것들은
`lib/report/mapWorkflowToFinalReport.ts` 에서 **성적서 문서를 그릴 때만** 쓰인다.

그런데 `isBasicInfoValid` 가 12개(taskType 포함)를 전부 필수로 걸어서, **평가와 무관한
11개 입력이 평가 앞을 막고 있다.** 모델 성능이 궁금해서 온 사람이 사업자등록번호를
쳐야 다음으로 간다.

백엔드는 이미 `evaluation/` 과 `issuance/` 로 나뉘어 있다. **프론트만 붙여 놨다.**


### 2.1 착수 후 순서가 바뀌었다 (업로드 먼저)

계획은 "지표 먼저 → 업로드"였다(아래 옛 근거). 실제로는 **업로드를 1단계로** 옮겼다.

사용자의 머릿속 순서가 그렇기 때문이다 — 평가하려는 데이터가 손에 있는 상태에서
시작하지, 지표 목록부터 읽고 시작하지 않는다. 업로드 화면은 이제 "선택한 지표에 필요한
컬럼"이 아니라 `getRequiredColumnsForTaskType` 으로 **그 유형이 쓸 수 있는 컬럼 전체**를
안내한다. 확률 컬럼을 포함한 예시를 기본으로 보여주는 것도 같은 이유다 — 나중에
"확률이 없어서 AUROC 를 못 쓴다"를 알게 되는 것보다 처음에 알려주는 편이 낫다.

**검증은 매핑 바로 뒤에 둔다.** 검증 결과가 평가에 쓰이므로 매핑과 붙어 있어야 한다.

지표 선택이 매핑보다 **앞**인 것은 백엔드 제약이다. `/api/evaluate` 의
`selected_metric_ids` 가 `Field(min_length=1)` 이라(`evaluation/schemas.py`) 빈 배열이면
422 가 난다. 백엔드를 건드리지 않기로 했으므로 순서로 푼다.

> 옛 근거(보존): "`DataUpload` 는 선택한 지표에 필요한 컬럼을 계산해 보여주므로
> (`getRequiredColumnsForSelection`) 순서를 뒤집으면 그 화면의 근거가 사라진다."
> — 화면의 안내 기준을 지표에서 **유형**으로 바꾸면서 이 근거가 해소됐다.

### 2.2 아이콘

`lucide-react` 에 "멀티레이블"을 뜻하는 아이콘은 없다. 원 몇 개짜리 **인라인 SVG를
직접 만든다** — 개념을 그대로 그리는 편이 텍스트 설명보다 빠르다.

> 아이콘 도형 규칙·진입 화면·유형 배지는 `docs/UI_DESIGN.md` 에서 다룬다.

| 유형 | 그림 | 한 줄 |
|---|---|---|
| Binary | ○● (2개 중 1개 채움) | 샘플 하나가 **둘 중 하나** |
| Multi-class | ○●○○ (4개 중 1개) | 샘플 하나가 **여럿 중 하나** |
| Multi-label | ●●○● (4개 중 3개) | 샘플 하나에 **여러 개** |

단계 탭은 lucide 로 충분: `ListChecks` · `Upload` · `Columns3` · `ShieldCheck` · `FileText`.

## 3. 단계 번호 대응표 ★

착수 전 이 표가 이 문서의 핵심이었다. 번호가 8개 파일에 **이름 없는 생짜 숫자**로 박혀
있어서, 타입이 전부 `number` 라 어긋나도 컴파일러가 안 잡았기 때문이다.

지금은 `useWorkflowStore.ts` 의 `STEP` 상수가 단일 출처다 — 표가 아니라 **코드가**
대응을 들고 있다.

```ts
export const STEP = {
  UPLOAD: 1, METRICS: 2, MAPPING: 3, VALIDATION: 4, SUMMARY: 5, RESULT: 6,
} as const;
```

| 구 | 화면 | 신 | 처리 |
|---|---|---|---|
| 1 | basic-info | **—** | **분해**: `taskType` → 진입 화면 / 모델명·버전 → 1 / 나머지 → 성적서 구간 |
| 2 | metrics | **2** | 구 3 의 β 를 흡수 |
| 3 | metric-detail | **—** | **페이지 삭제**. β → 2, 목표값 → 성적서 구간 |
| 4 | data-upload | **1** | 맨 앞으로(§2.1) |
| 5 | column-mapping | **3** | |
| 6 | data-validation | **4** | |
| — | evaluation-summary | **5** | **신규**. 검증과 성적서 사이, 고른 지표의 값만 |
| 7 | report | **6** | |

5·6 은 run 하나에 매인 화면이라 `/app/*` 이 아니라 `/report/:id/*` 아래 있다
(`RUN_SCOPED_STEPS`). `/app/*` 에 두면 어느 run 을 보는지 URL 이 말하지 못해
새로고침·공유·뒤로가기가 전부 깨진다.

### 3.1 구 3단계를 흡수하는 이유

`pages/MetricDetail.tsx` 는 **지표 하나당 화면 하나**인 위저드다("Next metric"). 추천
지표가 8개라 **8번 눌러야** 다음 단계에 간다. 그런데 각 화면이 묻는 건 대부분
**숫자 하나**(목표값)이고, β는 M5 하나뿐이다. 표 하나면 끝난다:

```
지표              목표값     비고
M1  Accuracy      [0.95]
M5  F-beta        [0.90]    β [1.0]
M21 Confusion     —         목표값 없음
```

8화면 → 1화면. **가장 싸고 체감이 큰 개선.**

### 3.2 선행 작업 — 번호에 이름을 붙인다 (완료)

숫자를 바꾸기 **전에** 생짜 숫자를 명명 상수로 바꿨다. 덕분에 착수 후 순서가 한 번 더
바뀌었을 때(§2.1) 한 곳 수정으로 끝났다. **"컴포넌트화"의 실질이 여기 있다.**

### 3.3 persist 마이그레이션 (v2 → v3, 완료)

`completedSteps` 는 **숫자 배열로 localStorage 에 저장돼 있다**. 번호 체계가 바뀌면
기존 브라우저에 남은 `[1,2,3,4,5]` 가 딴 뜻이 된다 — 빈 상태로 뒤 단계에 진입하거나,
반대로 마친 단계가 잠긴다.

계획은 구↔신 번호를 1:1 매핑하는 것이었으나, **실제로는 초기화한다**:

```ts
// v2 → v3
{ completedSteps: [], currentStep: STEP.UPLOAD }
```

순서가 뒤집히고(업로드가 4→1) 화면이 하나 생기면서 1:1 대응이 성립하지 않기 때문이다.
잘못 대응시켜 "마쳤다"고 표시된 단계가 실은 빈 상태인 것보다, 처음부터 다시 걷게 하는
편이 안전하다 — 어차피 원본 파일은 브라우저가 보관하지 못해 재업로드가 필요하다.

### 3.4 라우트

| 경로 | 처리 |
|---|---|
| `/app` | **진입 화면**(신규). 현재는 `/app/basic-info` 로 redirect |
| `/app/basic-info` | `/app` 으로 redirect (기존 북마크 보존) |
| `/app/metric-detail` | `/app/metrics` 로 redirect (페이지 삭제) |
| 레거시 `/step/*` | 현행 redirect 유지 |

## 4. 이번 범위에서 하는 것

| # | 항목 | 근거 절 |
|---|---|---|
| 1 | 단계 번호를 명명 상수로 (`STEP`) | §3.2 — 나머지 전부의 선행 조건 |
| 2 | 분류 유형 선택 진입 화면 + 아이콘 3장 | §1.1, §2.2 |
| 3 | 헤더에 유형 배지 상시 노출 | §1.1 |

| 6 | persist v2 → v3 마이그레이션 | §3.3 |

### 4.1 백엔드 변경 없음

확인함. 회사 정보는 `IssueRequest.content`(`dict | None`) 안에 통째로 실리고, 백엔드는
그 안을 들여다보지 않는다 — 크기만 검사한다(1 MiB, `issuance/schemas.py`). 필수 필드도
없다. **언제 회사 정보를 받든 백엔드는 알지 못한다.**

> 다만 이 유연함은 백엔드 `docs/ARCHITECTURE.md` §8.1 이 **F-02·F-03 으로 기록해둔
> 한계**와 같은 뿌리다 — 서버가 평가와 발급을 결속하지 않고 클라이언트가 보낸 내용을
> 그대로 믿기 때문에 순서를 자유롭게 바꿀 수 있다. 의도된 설계가 아니라 의식적으로
> 미뤄둔 항목이라는 점을 적어둔다.

`OrganizationOut` 은 의뢰기업이 아니라 **수행기관(performer)** 이고 서버가 시드한
고정값이다. 사용자 입력과 무관하다.

### 4.2 건드리지 않는 것 — 컬럼 매핑 화면

`components/column-mapping/DetectedMappingTable.tsx` 는 CSV 임포트 업계 표준 패턴
(업로드 컬럼 / 샘플 값 / 역할 드롭다운 + 문제 행 필터)을 이미 따르고 있다. 그대로 둔다.

**자동 매핑 신뢰도는 표시하지 않기로 한다.** 신뢰도가 의미 있는 건 "높으면 건너뛴다"는
선택지가 있을 때인데, 이 화면은 **사용자가 모든 행을 확정하는 것 자체가 목적**이다.
건너뛸 수 없다면 신뢰도는 정보가 아니라 잡음이다. 이 화면의 목표는 "확정을 빠르게"이고,
이미 있는 "Issues only" 필터가 그 레버다.

## 6. 이번 범위에서 뺀 것 + 왜

각 항목에 **왜 제외했는지**를 남긴다 — 근거를 잃으면 다음 사람이 같은 논의를 처음부터
다시 한다(백엔드 `docs/ARCHITECTURE.md` §8 의 방식을 따른다).

### 6.1 ~~업로드 먼저~~ → 했다. 다만 "계산 가능한 지표만 제시"는 여전히 안 한다

업로드를 앞으로 옮기는 것은 §2.1 대로 **했다**. 하지만 원래 묶여 있던
"계산 가능한 지표만 제시"는 **하지 않았고, 하지 않기로 한다.**

백엔드 `available_metric_ids` 는 매핑이 확정돼야 계산된다
(`analysis/validator.py`). 지표 선택이 매핑보다 앞이므로(§2.1) 지표 화면에서는 그 값이
아직 없다. 순서를 또 뒤집지 않는 한 성립하지 않는다.

대신 **"계산 가능한 지표 N/M" 문구를 제거했다**(`countComputableMetrics` 삭제).
전부 계산 가능할 때도 'N/N' 이 떠서 읽고 할 일이 없는 문구였고, 고른 지표가 조용히
빠지는 것은 매핑 화면이 필수 역할 누락을 직접 막아 이미 방지된다
(`resolveMissingRoleCodes` → `getMappingValidityReason`).

### 6.2 여러 워크플로우 동시 진행

현 구조는 `WORKFLOW_STORAGE_KEY = "ml-evaluation-workflow"` **단일 키**라 진행 중인
작업이 항상 하나다. 이진 평가를 하다 멀티클래스를 시작하면 앞의 것이 날아간다.
`useWorkspaceStore` 는 **끝난 run** 만 담고 **진행 중인 초안**은 담지 못한다.

필요한 변경:
```ts
// 지금:  { taskType, selectedMetricIds, ... }          ← 하나
// 목표:  { activeDraftId, drafts: Record<id, Draft> }  ← 여러 개
```

**제외 이유**: 스토어 형태 자체가 바뀌어 persist 마이그레이션이 §3.3 보다 훨씬 크고,
`WorkflowShell`·`StepTabs`·모든 페이지가 "현재 초안"을 경유하도록 바뀌어야 한다.
3일 범위가 아니다. **교수님 피드백의 "여러 워크플로우"에 대한 답은 이번엔 설계까지다.**

### 6.3 UI 한국어화

않는다"의 가장 큰 원인일 수 있다.

**제외 이유**: 번역 자체는 단순하나 기존 테스트가 영문 문자열을 찾고 있어

## 8. 워크스페이스 → 모델 → 버전 (2026-09-20)

### 8.1 왜 생겼나

평가는 일회성이 아니다. 실제 사용 패턴은 이렇다.

```
평가한다 → 성능이 아쉽다 → 모델을 고친다 → 다시 잰다 → 조금 올랐다 → 반복
```

그런데 워크스페이스 상세는 모든 평가를 **생성일순 한 테이블**로 보여줬다. 같은 모델의
v1.0·v1.1 과 전혀 다른 모델이 뒤섞이니, 사용자가 실제로 궁금해하는 "이 모델이 전보다
나아졌나"를 성적서 여러 개 띄워놓고 눈으로 맞춰봐야 했다.

계층이 셋으로 갈라진다:

| 층 | 무엇인가 | 어디 있나 |
|---|---|---|
| 워크스페이스 | 하나의 시험 프로젝트. 모델 이름의 네임스페이스이자 묶음 삭제 단위 | `Workspace` |
| 모델 | 비교 단위. **별도 엔티티가 아니라** run 의 `modelName` 으로만 존재한다 | — |
| 버전 | 평가 1회 | `WorkspaceEvaluationRun` |

모델을 엔티티로 만들지 않은 이유: 이름이 같으면 같은 모델이라는 규칙만으로 충분하고,
엔티티를 만들면 이름 변경·병합·고아 처리가 전부 따라온다. 지금 필요한 것은 묶어서
보여주는 것뿐이다.

### 8.2 선행 조건 — 모델명·버전을 업로드 화면으로

`modelName`·`versionName` 은 `basicInfo` 에 있어서 §1.2 에 따라 성적서 구간으로 갔다.
그 결과 **평가만 하고 끝낸 run 이 전부 `"Untitled model"` 로 저장됐다**
(`DataValidation.tsx` 의 `store.basicInfo.modelName || "Untitled model"`). 그러면
모델별로 묶을 수도, 비교할 수도 없다.

이 둘만 업로드 화면으로 되돌렸다. **성적서 서식용 값이 아니라 평가 결과를 식별하는
이름표**이기 때문이다 — 회사명·사업자번호·주소와는 성격이 다르다. 성적서 기본정보
화면에는 읽기 전용 표시만 남겼다(편집 지점이 둘이면 어느 쪽이 참인지 알 수 없다).

### 8.3 `Edit` → `New version`

종전 버튼 이름은 동작과 어긋나 있었다. 실제로 하는 일은 과거 평가를 **고치는** 것이
아니라, 입력을 물려받아 **run 을 하나 더 만드는** 것이다. 고치는 동작이었다면 이력이
덮여 비교할 대상이 남지 않는다.

버전은 맨 끝 숫자만 한 칸 올려 제안한다(`nextVersionName`). semver 를 해석하려 들면
`v2.0-beta`·`2024.09` 같은 이름에서 틀린 답을 자신 있게 낸다. 업로드 화면의 Version
입력이 열려 있으므로 제안이 빗나가도 사용자가 고친다.

**버튼은 행이 아니라 모델 카드 머리에 하나만 둔다.** 이 동작이 거는 대상은 특정 run 이
아니라 모델이다 — 행마다 놓으면 버전이 셋일 때 같은 뜻의 버튼이 셋이 된다. 물려받는
입력은 **가장 최근 버전**의 것이다(다음 버전은 직전 버전에서 잇는다).

그 대가로 **옛 버전에서 갈라져 나오는 길은 없앴다.** 스냅샷이 나르는 것은 유형·지표·
매핑·목표값이고 파일은 어차피 다시 올려야 하므로, 틀린 버전에서 이어받아도 흐름 안에서
고치면 된다 — 버튼 세 개를 유지할 만한 값어치가 아니다.

### 8.4 비교 화면 — **판정하지 않는다**

`/workspaces/:workspaceId/models/:modelName`. 표 둘로 되어 있다.

```
평가 데이터   행=속성, 열=버전    표본 수 / 클래스 목록 / 클래스별 개수 / 파일명
평가 결과     행=버전, 열=지표    최신이 맨 위, 없는 값은 '—'
```

증감 화살표도, 색도, "개선됨"도, **"같은 데이터로 보입니다"도 넣지 않는다.** 두 가지
이유다.

1. **숫자가 올랐다고 좋은 것인지는 사용자가 판단한다.** 모델의 용도와 오류 비용을
   아는 사람만 아는 일이다.
2. **"같은 데이터인가"는 우리가 확언할 수 없다.** 데이터를 식별하는 값은 y_true 기반
   `class_distribution` 인데(y_pred 는 모델이 좋아지면 **설계상** 바뀌므로 식별자가
   될 수 없다), 멀티레이블에서는 이것이 레이블 등장 횟수라 동시 출현을 잃는다 —
   `{A,B},{}` 와 `{A},{B}` 가 똑같이 `A:1, B:1` 이 된다. 틀릴 수 있는 확언을
   자신 있게 띄우느니 **사실만 나열하고 판단을 넘긴다.**

파일명은 보여주되 비교 기준으로 쓰지 않는다 — 같은 파일을 다른 이름으로 저장하는 일도,
같은 이름의 다른 파일을 올리는 일도 흔하다.

표본 수의 출처에 주의가 필요하다. `datasetInfo.sampleCount` 는 사용자가 성적서 구간에서
손으로 적는 값이라 평가만 한 run 에서는 0 이다. 서버가 확정한
`validationSummary.totalRows` 를 먼저 쓰고, 없으면 혼동행렬의 `totalSamples` 를 쓴다.
확정값이 하나도 없으면 `null` 로 두고 '—' 를 그린다 — **0 행으로 읽히면 안 된다.**

### 8.5 들어가는 길 둘

```
Workspaces → 워크스페이스 → 모델 카드의 [Compare]
평가 결과 화면(5단계) → [Compare versions]
```

두 번째가 있는 이유: 평가를 막 끝낸 직후가 "전보다 좋아졌나"가 가장 궁금한 순간이라,
워크스페이스까지 되돌아가지 않아도 되게 한다. 둘 다 **평가가 둘 이상일 때만** 뜬다 —
비교할 대상이 없는 버튼은 안 보이는 편이 낫다.

### 8.6 남은 것

- **워크스페이스의 성격**: 지금은 이름·설명뿐인 껍데기에 가깝다. 회사명·사업자번호·주소가
  평가마다 반복 입력되는데 이 값들은 프로젝트 내내 안 바뀌므로, 워크스페이스 속성으로
  올리면 반복이 사라지고 워크스페이스에 존재 이유가 생긴다. 다만 그러면
  `pages/report/ReportInfo.tsx` 가 목표값만 남아 비어버려서, 그 화면을 어떻게 할지가
  같이 정해져야 한다. **미결.**
- **데이터 동일성의 엄밀한 판정**: 백엔드가 y_true 해시를 내려주면 멀티레이블에서도
  확언할 수 있다. 백엔드 변경이 필요해 이번 범위 밖(§6.2 와 함께).

## 9. 단계 목록을 계산으로 (2026-10-03, 브랜치 `feature/report-composer`)

> §3 은 "코드가 대응을 들고 있다"고 적었다(`STEP` 상수). 그 전제가 바뀌었다 —
> **단계 목록이 사용자의 선택에서 계산된다.** 낡은 기록을 지우지 않고 무엇이 왜 바뀌었는지 남긴다.

### 9.1 왜 바꾸나

성적서 구성 화면이 생겼다(`docs/COMPOSER_COMPONENTS.md`). 사용자가 선택 카드 ⑥~⑨를 켜고 끄면
그 카드의 입력 단계만 만들어지므로, 걸을 단계가 **8개(최소 구성)에서 10개(전체)** 사이로 달라진다.

고정 번호로는 성립하지 않는다. 카드를 끄면 뒤 단계의 번호가 당겨져, 저장된 `completedSteps` 의
`[1,2,3,4]` 가 딴 뜻이 된다 — §3.3 이 경고한 바로 그 상황이 **선택을 바꿀 때마다** 일어난다.

### 9.2 세 벌이던 정의를 하나로

| 종전 | 어디 | 지금 |
|---|---|---|
| `STEP` (번호) | `useWorkflowStore.ts` | `StepId` 문자열 union (`types/workflow.types.ts`) |
| `STEP_PATHS` (경로) | `useWorkflowStore.ts` | `STEP_CATALOG` (`data/workflowSteps.ts`) — 라벨·아이콘·경로·조건을 함께 든다 |
| `steps` (라벨·아이콘) | `StepTabs.tsx` 지역 배열 | 위 카탈로그 |

셋을 묶는 것이 **배열 위치**뿐이어서 주석으로 경고해야 했던 구조가 사라졌다.
`LAST_STEP` 은 소비자가 0개여서 삭제했다.

걸을 목록은 `utils/domain/workflowSteps.ts` 의 `buildStepList(composerCards)` 가 만든다.
`canEnterStepId`·`resumeStepId`·`stepIdToPath`·`pathToStepId` 도 같은 파일에 있고,
`utils/domain/stepAccess.ts` 는 이것들로 대체돼 삭제했다.

### 9.3 산수가 사라진 자리

| 종전 | 문제 | 지금 |
|---|---|---|
| `canEnterStep`: `step - 1` 이 선행 단계 | 카드를 끄면 번호가 당겨져 틀린 단계를 본다 | 계산된 목록의 **직전 항목** |
| `resumeStep`: `Math.max(...) + 1` | 중간에 구멍이 있으면 빈 화면으로 보낸다 | 목록에서 **처음 미완료** |
| `pathToStep`: 미지 경로를 조용히 **1** 로 | `/report/*` 가 전부 1단계가 돼, 평가 결과 화면이 `useEffect` 로 자기 단계를 되돌려 놔야 했다 | `pathToStepId` 가 run 경로까지 알아보고, 단계가 아니면 `null` |
| 다음/이전 목적지 | 5개 화면 × 2방향 = 간선 10개가 하드코딩(둘은 경로 문자열 직접) | `hooks/useStepFlow.ts` 가 목록에서 유도 |

`STEP_PATHS[4]="evaluation-summary"`·`[5]="report"` 는 **라우트가 없는 유령 세그먼트**였다.
카탈로그는 run 경로를 `runScoped`·`runSegment` 로 명시해 그 틈을 없앴다.

### 9.4 persist 마이그레이션 (v3 → v4 → v5)

**v3 → v4 — 성적서 구성 상태 추가.** `composerCards` 와 입력 그룹 5개가 생겼다.
**버릴 것이 없다** — 기존 키의 뜻이 하나도 바뀌지 않았고 새 키만 생겼으므로 기본값으로 채운다.

채우는 것이 필수인 이유: zustand 의 merge 는 **얕다.** 옛 저장분에 없는 키는 초기 상태의
값으로 채워지지 않고 `undefined` 로 남고, 그 상태로 구성 화면이 열리면 체크박스가 `undefined` 를
읽어 선택 카드가 하나도 안 켜진 것처럼 보인다. v1 → v2 처럼 저장분을 직접 패치한다.

**v4 → v5 — 진행 표시를 번호에서 이름으로.**

```ts
// 구 1~6 → StepId
const LEGACY_STEP_IDS = ["upload","metrics","mapping","validation","summary","report"];
```

§3.3 과 **반대 결정이다**: 거기서는 1:1 대응이 성립하지 않아 초기화했지만, 여기서는 구 1~6 이
가리켰던 단계가 새 체계에 그대로 있고 순서도 같다(사이에 평가 관점이 끼어들었을 뿐이다).
그래서 **진행을 버리지 않고 옮긴다** — 다 걸어온 사용자를 다시 1단계로 돌려보낼 이유가 없다.

새로 생긴 단계(평가 관점·데이터 정보·모델과 환경·의뢰자 정보)는 미완료로 남는다. 가드가
사용자를 처음 미완료 단계로 보내는데, 그 입력을 실제로 받아야 하므로 **옳은 동작**이다.

### 9.5 한 가지 의도적인 예외 — run 에 매인 화면은 가드하지 않는다

가드가 막으려는 것은 **빈 상태로 입력 단계에 들어가는 것**이다(E-12·E-13·E-04). 반면
`/report/<runId>/...` 는 저장된 run 을 **보여주는** 화면이고, 전제 조건은 "그 run 이 있는가"다 —
진행 표시가 아니라 `useReportData` 가 확인한다. 진행 표시로 막으면 URL 로 공유받은 성적서가
열리지 않는다.

종전 동작과도 같다. `pathToStep` 이 `/report/*` 를 1단계로 돌려줘 가드가 늘 통과했다 —
달라진 것은 **단계 표시가 올바르게 맞는다**는 점뿐이다.

### 9.6 고친 낡은 문구

| 위치 | 종전 | 왜 틀렸나 |
|---|---|---|
| `UnevaluatedDraftNotice.tsx` | "**6단계**로 돌아가 평가 다시 실행" | 링크는 `/app/data-validation`(당시 4단계)였다. 테스트가 이 오류를 고정하고 있었다 |

`utils/domain/mappingValidity.ts` 가 이미 세운 선례를 따랐다 — 안내 문구는 단계를 **번호가
아니라 이름으로** 가리킨다(`mappingValidity.test.ts` 가 번호가 없음을 강제한다).

### 9.7 이번에 하지 않은 것

- **`README.md`·`docs/ARCHITECTURE.md`·`SPEC.md` §6·`docs/imports/*` 의 단계 번호 정정.**

  매핑·검증을 5·6단계로 쓴다). 문서 정정은 코드 변경과 섞지 않는다.

  와 `/app/basic-info` 경로). 마케팅 화면이라 워크플로우와 분리돼 있다.

## 10. 단계 이름·언어·필수 입력 정리 (2026-10-04, 브랜치 `feature/report-composer`)

§9 로 단계 목록이 카드 선택에서 계산되기 시작한 뒤, 전체 카드를 켜고 끝까지 걸어 보니 네
가지가 걸렸다. 모두 화면 쪽 문제고 백엔드 요청 형식은 건드리지 않았다.

### 10.1 평가 관점을 지표 선택 화면으로 (10 → 9단계)

⑤ 평가 관점은 질문이 **둘**뿐인데 단계 하나를 차지하고 있었다. 그 둘(중대 오류 유형 또는
클래스 우선순위, 사용 방식)은 곧 **어떤 지표를 권할지 정하는 근거**라, 고르는 화면과 떨어뜨릴
이유가 없다. 단계를 지우고 지표 선택 화면 맨 위로 옮겼다.

- `StepId` 에서 `"perspective"` 제거, `STEP_CATALOG` 9개
- 전체 카드 **9단계**, 최소 구성 **7단계** (종전 10 / 8)
- `/app/perspective` 는 `/app/metrics` 로 리다이렉트 — 저장된 링크가 죽지 않게
- `buildStepList` 는 그대로 둔다. `dataInfo`·`modelEnv` 가 여전히 조건부 단계다

**합치지 않은 것**: Data info·Model info·Details 는 단계로 남겼다. 한때 7단계로 모두 합치는
안이 있었지만, 이 셋은 각각 받는 것이 분명히 다르고 조건부라 대부분의 사용자에게는 애초에
나타나지 않는다(최소 구성이면 7단계다).

### 10.2 단계 이름을 화면이 받는 것에 맞춤

| 전 | 후 | 이유 |
|---|---|---|
| Data upload | **Evaluation File** | 올리는 것은 평가할 결과 파일이다 |
| Model & environment | **Model info** | 짧고, 설정과 실행 환경을 함께 덮는다 |
| Report details | **Details** | 성적서 구간 안이라 "Report" 가 겹친다 |

### 10.3 구성·입력 화면을 영어로, 카드 번호는 화면에서 제거

카드 제목 앞의 ① ~ ⑨ 는 사용자에게 뜻이 없는 기호다. 화면에서 빼고 레지스트리의 `number`
필드만 남겼다 — `docs/COMPOSER_COMPONENTS.md` 와 코드를 잇는 유일한 고리다.

문구는 레지스트리 **전체**(①~⑨)를 영어로 옮겼다. ⑥~⑨ 만 옮기면 구성 화면이 다시 한/영
혼합이 된다 — 레지스트리가 구성 화면과 입력 화면의 단일 출처이기 때문이다. `RemainingNotice`
가 들고 있던 `lang` prop 도 함께 지웠다.

> **선택지와 칸 이름은 저장되는 값이다.** `choices`·`entryKeys` 는 화면 라벨이면서 스토어에
> 들어가는 문자열 자체다. 옮기면 저장된 값이 어느 선택지와도 맞지 않아, 라디오는 빈 채로
> 열리는데 필수 점검은 통과하는 모순이 생긴다. → persist **v6 → v7** 에서 ⑥⑦⑧⑨ 네 입력
> 그룹을 비운다(⑤ 는 선택지가 이미 영어라 남긴다).

⑨ 실행 환경의 다섯 칸은 이제 영문(Operating system·CPU·GPU·Memory·Software)이지만 성적서는
그대로 "운영체제"로 인쇄한다. 무엇으로 인쇄할지는 `legacy.byKey` 가 정하므로 화면 문구와 묶어
둘 필요가 없다.

### 10.4 필수 표시와 차단

종전에는 다음 버튼이 **처음부터 비활성**이었다. 왜 막혔는지 알려면 하단 한 줄을 읽어야 했고,
그 줄이 이름을 말해 줘도 칸이 화면 밖이면 찾는 일이 또 숙제였다. 무엇이 필수인지 칸 옆에
표시도 없었다.

- 필수 칸 라벨에 빨간 `*`. 기준은 `isFieldRequired(field, values)` 라 조건부 필드는 조건이
  성립해 **실제로** 필수가 될 때만 붙는다. 모양은 기존 폼의 `Field` 와 같다
- 다음 버튼을 누를 수 있게 하고, 누르면 `showErrors` 를 켜 빈 필수 칸마다 `Required.` 를 적고
  `focusFirstIssue` 로 첫 칸으로 옮긴 뒤 막는다
- **들어오자마자는 칠하지 않는다** — 아무 일도 하지 않은 사용자를 꾸짖지 않는다. 배타 선택처럼
  지금 당장 틀린 것만 바로 표시한다
- 지표 격자는 종전대로 잠근다. 눈앞에 격자가 있어 무엇을 해야 할지 이미 보인다

### 10.5 선택지를 네모 타일로

16px 짜리 동그라미 하나는 과녁이 작고 글자는 과녁에 들어 있지도 않았다. `RadioGroupItem` 에
`shape="square"` 를 더해 체크박스와 같은 모양으로 만들고(역할은 그대로 `radio`), 선택지 한
줄을 `<label>` 로 감쌌다. 고른 줄은 구성 화면의 카드와 같은 규칙 — 굵은 파란 테두리 + 연한
파랑 바탕, 여백 1px 보정으로 줄 높이 유지. `Unknown` 도 같은 모양의 토글이다. 새 색은 만들지
않았다(`--primary`·`--primary-subtle`·`--border-strong`).

### 10.6 아직 하지 않은 것

- **Details 의 Test environment·Training dataset information 폼.** ⑨·⑥ 과 값이 겹치지만
  **그대로 두었다.** 카드를 켠 사용자는 같은 값을 두 번 적게 되고, 안 켠 사용자는 Details
  에서만 적을 수 있다. 셋 중 어느 쪽으로 갈지(폼 삭제 / ⑥⑨ 를 필수 카드로 승격 / 양쪽 유지)
  는 다음 결정이다.
  - 겹치는 범위: ⑨ 실행 환경 ↔ `basicInfo.env*` 다섯이 1:1. ⑥ ↔ `datasetInfo` 는 데이터
    이름·학습/검증 건수·클래스 분포가 겹치고 **Training data format 하나만** ⑥ 에 없다.
- **`composerLegacyMirror` 배선.** 위가 정해지기 전에 카드 값을 기존 저장소로 흘려보내면,
  사용자가 Details 에서 고친 값을 카드 값이 조용히 덮는다. 함수와 테스트만 둔다.
- 새 카드 필드의 성적서 인쇄 · 합격 기준을 Metrics 로 옮기기 · 평가 표본 수 인쇄 버그
  (`mapWorkflowToFinalReport.ts:89,191`) · 문서의 단계 번호 정정.
