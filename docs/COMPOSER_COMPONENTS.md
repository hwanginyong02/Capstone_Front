# 성적서 구성 컴포넌트 설계

Oct 3, 2026 · @인용

## 개요

성적서 구성 화면은 카드 9개(필수 5개, 선택 4개)로 이루어지며, 사용자는 선택 카드를 켜고 끄는 것만으로 자신만의 시험성적서를 구성한다. 지도교수 피드백에 따라 단계별로 받던 입력을 컴포넌트로 묶어, 한 화면에서 고르고 "다음"을 누르면 고른 카드의 입력 단계만 만들어진다.

전체 흐름은 다음과 같다.

1. 분류 유형 선택 (이진 / 다중 클래스 / 멀티레이블)
2. 성적서 구성 (카드 고르기)
3. 카드별 입력 단계 (고른 카드만)
4. 검증과 평가
5. 성적서 생성과 발급

각 카드에는 네 가지만 보여준다.

- **설명**: 이 카드가 무엇인지 한 문장
- **필드**: 카드 안에서 입력할 항목
- **입력 방식**: 실제 값을 예시로 보여준다 (예: `전문가 수동 / 크라우드소싱 / …`)
- **구분**: 필수 / 보고 / 선택 / 조건부

성적서 위치와 AI 전달 여부는 개발자용 정보라 카드에 보이지 않고, 코드의 재료 레지스트리에만 둔다.

## 카드를 나눈 기준과 구분 규칙

카드와 필드는 세 가지 기준으로 나눴다.

- 성적서의 **절이나 표가 생기고 사라지면 카드**, 같은 칸의 **내용만 바뀌면 필드**로 둔다.
- 업로드 파일 안의 컬럼(확률 점수, 응답시간 등)은 따로 줄 수 없으므로 **평가 데이터 카드에서 파일로 받고**, 컬럼 매핑 단계에서 확인한다.
- 기본값이 있거나 있으면 좋은 정도의 항목은 **더보기**로 접어 카드에 보이는 필드를 줄인다.

구분은 네 가지다.

| 구분 | 뜻 | 비우면 |
| --- | --- | --- |
| 필수 | 성적서가 성립하는 데 꼭 필요한 값 (재료 선택 점검 1층) | 다음 단계로 진행할 수 없다 |
| 필수 (표준 보고) | TS 4213이 성적서에 적으라고 요구하는 항목 (재료 선택 점검 2층). 카드를 켜면 반드시 입력해야 하고, 모르면 "모름"을 고른다 | 다음 단계로 진행할 수 없다. "모름"을 고르거나 카드를 끄면 성적서에 "제공되지 않음"으로 찍힌다 |
| 선택 | 성적서를 풍부하게 하는 값 | 그 칸이 빠진다 |
| 조건부 | 특정 조건에서만 나타나고, 나타나면 필수 | 조건에 따라 다르다 |

선택지에서 "모름"을 고르면 "제공되지 않음"으로 센다. 단, 수집 환경 차이(채널 효과)의 "알려진 것 없음"은 원문이 요구하는 답이라 제공된 것으로 센다. 작업 유형에 원래 없는 항목은 카드에서 숨기고 성적서에는 "해당 없음"으로 적는다.

## 카드 9개 한눈에 보기

필수 카드 5개는 잠겨 있어 뺄 수 없고, 선택 카드 4개는 끄면 그 안의 표준 보고 항목이 "제공되지 않음"으로 찍힌다.

| 카드 | 구분 | 설명 | 적용 유형 |
| --- | --- | --- | --- |
| ① 평가 데이터 | 필수 | 예측 결과 파일 올리기 | 전부 |
| ② 지표와 합격 기준 | 필수 | 평가 지표와 목표 기준 | 전부 |
| ③ 의뢰자 정보 | 필수 | 성적서를 받는 회사와 용도 | 전부 |
| ④ 평가 대상 모델 | 필수 | 모델 이름과 쓰임새 | 전부 |
| ⑤ 평가 관점 | 필수 | 이 모델에서 무엇을 중요하게 볼지 | 전부 (필드는 유형별로 다름) |
| ⑥ 학습 데이터 | 선택 | 모델을 훈련할 때 쓴 데이터 | 전부 |
| ⑦ 테스트 데이터 | 선택 | 성능을 잰 테스트 데이터의 출처 | 전부 |
| ⑧ 정답 라벨 | 선택 | 테스트 데이터의 정답을 누가, 어떻게 붙였는지 | 전부 |
| ⑨ 모델 설정과 실행 환경 | 선택 | 모델 설정값과 실행한 컴퓨터 | 전부 |

재료 목록의 사용자 입력 항목(1\~8절)은 모두 이 9개 카드 중 하나에 들어간다. 시스템 계산 값(9절)은 사용자가 입력하지 않으므로 카드가 없고, 성적서 관리 항목(10절: 발급 확인, 정정 사유, 워크스페이스)은 성적서 내용이 아니라서 발급 단계에 둔다.

## 카드별 상세

각 카드는 설명 한 줄과 필드 표로 구성된다. 필드 이름은 명사로 쓰고, 뜻이 덜 전해지는 필드는 입력 화면에서 한 줄 도움말을 붙인다. 선택 카드(⑥\~⑨)의 "필수"는 카드를 켰을 때 필수라는 뜻이며, 모르면 "모름"을 고른다.

### ① 평가 데이터 (필수)

예측 결과 파일 올리기.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 결과 파일 | `predictions.csv` 업로드 (CSV·JSON, 20 MiB 이하) | 필수 |

카드에 **예시 파일 보기** 버튼을 두고, 누르면 선택한 분류 유형의 예시를 보여준다. 컬럼 매핑, 양성 클래스, 결정 임계값은 "다음" 이후 컬럼 매핑 단계에서 처리한다.

이진: 정답은 필수, 예측과 양성 확률(score) 중 하나는 필수. 확률이 있어야 AUROC 같은 곡선 지표를 쓸 수 있다. latency\_ms는 선택.

```csv
id,y_true,y_pred,score,latency_ms
S001,1,1,0.91,12
S002,0,1,0.62,9
S003,0,0,0.08,11
```

다중 클래스: 정답은 필수, 예측과 클래스별 확률(prob\_클래스명) 중 하나는 필수. 확률만 있으면 가장 높은 클래스를 예측으로 쓴다.

```csv
id,y_true,y_pred,prob_cat,prob_dog,prob_bird
S001,cat,cat,0.81,0.12,0.07
S002,dog,bird,0.10,0.35,0.55
S003,bird,bird,0.05,0.15,0.80
```

멀티레이블: 레이블은 | 로 구분하고, 빈칸은 레이블 없음이다. 정답은 필수, 예측과 레이블별 점수(score\_레이블명) 중 하나는 필수.

```csv
id,true_labels,pred_labels,score_sports,score_news
S001,sports|news,sports,0.92,0.41
S002,news,news,0.08,0.88
S003,,news,0.12,0.57
```

### ② 지표와 합격 기준 (필수)

평가 지표와 목표 기준.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 지표 | 선택한 분류 유형에서 고를 수 있는 지표 중 선택 (최소 1개) | 필수 |
| 합격 기준 | `Accuracy ≥ 0.85` (혼동행렬은 면제) | 필수 |
| β | `1.0` | Fβ 선택 시 |
| 지표 선택 이유 | `오차를 고르게 봄 / 모든 레이블 일치 / 겹치는 정도` | 필수 (멀티레이블만) |

카드에 **고를 수 있는 지표 보기** 버튼을 두고, 선택한 분류 유형의 지표만 보여준다. 핵심 지표는 더보기에 두고 유형별 기본 세트를 미리 체크한다.

| 분류 유형 | 고를 수 있는 지표 |
| --- | --- |
| 이진 (15개) | M1 Accuracy, M2 Precision, M3 Recall, M4 F1, M5 Fβ, M6 KL Divergence, M7 Specificity, M8 FPR, M9 AUROC\*, M10 AUPRC\*, M19 Log Loss\*, M20 MCC, M21 혼동행렬, M22 클래스별 지표, M23 불균형 비율 |
| 다중 클래스 (13개) | M1 Accuracy, M2 Precision, M3 Recall, M4 F1, M5 Fβ, M6 KL Divergence, M11 Macro 평균, M12 Micro 평균, M13 Weighted 평균, M14 분포 차이, M21 혼동행렬, M22 클래스별 지표, M23 불균형 비율 |
| 멀티레이블 (11개) | M2 Precision, M3 Recall, M4 F1, M5 Fβ, M15 Hamming Loss, M16 Exact Match, M17 Jaccard, M18 분포 차이, M21 혼동행렬, M22 레이블별 지표, M23 불균형 비율 |

\* 확률(score) 컬럼이 있어야 고를 수 있다.

멀티레이블에서는 M1 Accuracy를 고를 수 없다. TS 4213 6.5.1은 멀티레이블에서 정확한 일치율을 "이진 정확도를 조정한 것"으로, 6.5.3은 이를 "서브 세트 정확도"로 정의하므로 멀티레이블의 Accuracy는 M16 Exact Match와 같은 값이다. 백엔드도 같은 이유로 멀티레이블에서 M1·M11·M12·M13을 노출하지 않는다(app/core/schemas.py, 2026-09-07 결정 2).

### ③ 의뢰자 정보 (필수)

성적서를 받는 회사와 용도.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 회사 정보 | `(주)테스트기업 · 홍길동 · 123-45-67890 · 02-1234-5678 · 서울시 …` | 필수 |
| 성적서 용도 | `내부 검증 / 외부 제출 / 과제 제출` | 필수 |
| 과제 정보 | `과제명 · 과제 기관` | 과제 제출 시 |

더보기: 홈페이지·팩스, 과제 번호, 평가 의뢰일 (기본 오늘)

### ④ 평가 대상 모델 (필수)

모델 이름과 쓰임새.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 모델 이름·버전 | `ChurnPredictor · v1.0.0` (버전 기본 v1.0.0) | 필수 |
| 모델 용도 | `통신사 고객 이탈 예측` | 필수 |

### ⑤ 평가 관점 (필수)

이 모델에서 무엇을 중요하게 볼지. 필드는 분류 유형에 따라 다르며, 사용자는 항상 두 개를 받는다.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 중요 오류 유형 | `놓침(FN) / 잘못 잡음(FP) / 비슷함` | 필수 (이진) |
| 클래스 중요도 | `모두 동등 / 큰 클래스 우선 / 개별 샘플 우선` | 필수 (다중·멀티) |
| 사용 방식 | `실시간 응답 / 일괄 처리` | 필수 |

답에 따라 알맞은 지표를 추천하고, 고른 지표가 맞지 않으면 경고한다(진행은 막지 않는다). 값은 성적서 5절에 인쇄되고 AI 서술의 기준이 된다.

| 필드 | 선택지 | 확인하는 것 | 근거 (TS 4213) |
| --- | --- | --- | --- |
| 중요 오류 유형 | 놓침(FN) | Recall 또는 β가 1보다 큰 Fβ를 골랐는가 | 6.2.6 |
| 중요 오류 유형 | 잘못 잡음(FP) | Precision 또는 β가 1보다 작은 Fβ를 골랐는가 | 6.2.6 |
| 중요 오류 유형 | 비슷함 | 확인 없음 | 6.2.6 |
| 클래스 중요도 | 모두 동등 | 매크로 평균 지표를 골랐는가 | 6.4.3 |
| 클래스 중요도 | 큰 클래스 우선 | 가중 평균 지표를 골랐는가 | 6.4.3 |
| 클래스 중요도 | 개별 샘플 우선 | 마이크로 평균 지표를 골랐는가 | 6.4.3 |
| 사용 방식 | 실시간 응답 | 응답시간(latency) 컬럼이 있는가 | 6.6.2 |
| 사용 방식 | 일괄 처리 | 확인 없음 | 6.6.2 |

다중 클래스의 Accuracy는 마이크로 평균 지표로 인정하고, 클래스별 지표(M22)를 고르면 세 평균 방식이 모두 있는 것으로 본다.

### ⑥ 학습 데이터 (선택)

모델을 훈련할 때 쓴 데이터.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 데이터 이름 | `고객 로그 2024` | 필수 |
| 데이터 양 | `학습 12,000건 · 검증 3,000건` | 필수 |
| 클래스별 데이터 양 | `정상 8,400 / 이탈 3,600` (업로드한 클래스 목록으로 칸 생성) | 필수 |
| 수집 환경 차이 | `☐ 알려진 것 없음 ☐ 장비 차이 ☐ 전처리 차이 ☐ 수집자 차이 ☐ 수집 환경 차이 ☐ 기타(직접 입력)` (복수 선택) | 필수 |
| 불균형 보정 | `클래스 수 맞춤 / 출처 다양화 / 보정 안 함 / 모름` | 필수 |
| 수집 기간 | `2023-01 ~ 2024-12` | 선택 (더보기) |
| 전처리 여부 | `결측치 제거, 정규화` (직접 입력) | 선택 (더보기) |

도움말: 수집 환경 차이는 "같은 클래스의 데이터가 서로 다른 장비, 처리 방식, 사람, 환경에서 모였는지"(TS 4213 5.3.8 채널 효과)를 묻는다. 차이가 여러 개일 수 있어 복수 선택이고, "알려진 것 없음"은 다른 선택지와 함께 고를 수 없으며 제공된 것으로 센다. 불균형 보정은 "한쪽 클래스에 몰린 데이터를 보정했는지"(TS 4213 8절)를 묻는다.

### ⑦ 테스트 데이터 (선택)

성능을 잰 테스트 데이터의 출처. 건수와 클래스별 건수는 올린 파일에서 시스템이 센다.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 데이터 출처 | `2025년 1분기 고객 로그` (직접 입력) | 필수 |
| 학습 데이터와 출처 관계 | `같음 / 다름 / 모름` | 필수 |
| 수집 기간 | `2025-01 ~ 2025-03` | 선택 (더보기) |

도움말: 학습 데이터와 출처가 같으면 점수가 실제보다 좋게 나올 수 있어 성적서에 함께 적는다.

### ⑧ 정답 라벨 (선택)

테스트 데이터의 정답을 누가, 어떻게 붙였는지.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 라벨 작성 주체 | `전문가 / 외부 작업자 / 프로그램·규칙 / 실제 결과 기록` | 필수 |
| 라벨 검수 방식 | `복수 교차 검수 / 1인 검수 / 검수 없음 / 모름` | 필수 |
| 검수 인원·일치율 | `3명 · 82%` | 복수 교차 검수일 때 |

도움말: 정답이 틀리면 점수도 믿을 수 없어서 정답의 출처를 성적서에 적는다. 실제 결과 기록은 "실제 해지 여부"처럼 사후에 확인된 결과를 정답으로 쓴 경우다.

### ⑨ 모델 설정과 실행 환경 (선택)

## 카드별 입력 단계

구성 화면에서 고른 카드는 아래 단계에 매핑된다. 카드는 "성적서에 무엇이 들어가는가", 단계는 "언제 묻는가"라서 한 카드가 두 단계에 나뉘기도 한다(①, ④). 평가만 하는 사용자는 6단계에서 끝나고, 7\~10단계는 성적서를 발급할 때만 나타난다.

| 단계 | 구간 | 단계 이름 | 받는 카드·필드 | 나타나는 조건 |
| --- | --- | --- | --- | --- |
| 1 | 평가 | 데이터 업로드 | ① 결과 파일, ④ 모델명·버전 | 항상 |
| 2 | 평가 | 평가 관점 | ⑤ 전체 | 항상 |
| 3 | 평가 | 지표 선택 | ② 전체 | 항상 |
| 4 | 평가 | 컬럼 매핑 | ① 컬럼 매핑, 양성 클래스, 결정 임계값 | 항상 |
| 5 | 평가 | 검증·평가 실행 | — | 항상 |
| 6 | 평가 | 평가 결과 | — | 항상 |
| 7 | 발급 | 데이터 정보 | ⑥ ⑦ ⑧ 중 켠 카드 | 셋 중 하나라도 켰을 때 |
| 8 | 발급 | 모델과 환경 | ⑨ 전체 | ⑨를 켰을 때 |
| 9 | 발급 | 의뢰자 정보 | ③ 전체, ④ 모델 용도 | 항상 |
| 10 | 발급 | 성적서 | — | 항상 |

최소 구성이면 8단계(1\~6, 9, 10), 전체면 10단계가 된다.

순서는 다음 이유로 정했다.

- **1→3→4→5는 현재 구현 순서를 그대로 둔다.** 지표가 매핑보다 앞인 것은 백엔드가 지표 목록 없이 검증·평가 요청을 받지 않기 때문이다(WORKFLOW\_REDESIGN §2.1).
- **⑤ 평가 관점은 ② 지표 바로 앞**에 끼운다. 평가 관점이 지표 점검의 기준이라 먼저 받아야 "FN이 더 위험하니 Recall을 추천"처럼 지표를 미리 골라 줄 수 있다.
- **⑥ ⑦ ⑧ ⑨ ③은 발급 구간**에 둔다. 평가와 무관한 정보가 평가 진행을 막지 않게 하려는 기존 결정(평가와 발급의 분리)을 유지한다. ⑥의 학습 클래스 분포는 업로드한 클래스 목록이 필요한데, 발급 구간은 항상 업로드 뒤라 이 제약도 자연히 지켜진다.
- **재료 선택 점검은 9단계에서 10단계로 넘어갈 때 실행**한다. 서술 생성 전에 돌아야 하고, 이때 모든 입력이 확정된다.

## 구성 화면 레이아웃

세부 디자인(폰트, 색, 크기)은 다음 단계에서 정하고, 여기에는 배치만 둔다.

1. **맨 위**: 선택한 분류 유형 표시, 화면 제목 "성적서 구성", 프리셋 버튼(최소 구성 / 전체)
2. **필수 카드 줄**: ①\~⑤를 한 줄에 가로로 놓는다. 자물쇠 표시, 끌 수 없다.
3. **선택 카드 줄**: ⑥\~⑨를 그 아래 한 줄에 가로로 놓는다. 왼쪽 위 체크박스로 켜고 끈다(기존 Selectable Card와 같은 위치).
4. **상세 영역**: 카드를 누르면 카드 줄 아래 여백에 그 카드의 설명과 필드 표가 나온다. 한 번에 한 카드만 보이며, 화면에 들어오면 ①이 선택된 상태로 시작한다. ①에는 예시 파일 보기, ②에는 고를 수 있는 지표 보기 버튼을 둔다.
5. **하단 바**: 요약 한 줄(분류 유형 · 선택 카드 n/4 켜짐 · 입력 단계 n개)과 다음 버튼.

카드를 **누르는 것**(상세 보기)과 **켜는 것**(체크박스)은 분리한다. 합치면 내용을 보려고 눌렀다가 카드가 꺼지는 일이 생긴다. 하단 요약은 레지스트리에서 계산하며 AI 호출이나 서버 요청은 없다.

## 결정 사항과 열린 결정

**프리셋은 "최소 구성"과 "전체" 두 가지로 한다.** 최소 구성은 필수 카드 5개만, 전체는 필수 5개와 선택 4개를 모두 켠다. 더보기 필드는 프리셋과 무관하게 입력 단계에서 펼쳐 쓸 수 있다.

**⑤ 평가 관점은 구성 화면이 아니라 입력 단계(2단계)에서 받는다.** 질문이 늘어날 수 있어 구성 화면에 두면 화면이 무거워진다.

평가 관점은 사용자가 선택지로 답하는 **고정 질문**이다. AI가 만드는 질문이 아니고, 모델마다 달라지지도 않는다. 분류 유형에 따라서만 달라진다.

질문은 늘어날 수 있지만, 새 질문은 두 가지를 갖춰야 한다. TS 4213의 근거 조항이 있어야 하고, 그 답이 요구하는 재료(점검 줄, 예: "대화형이면 지연시간 필요")가 정해져야 한다. 점검에 쓰이지 않는 질문은 평가 관점이 아니라 일반 입력 필드다.

남아 있던 열린 결정도 정했다.

- [x] **선택 카드를 켠 뒤 보고 필드를 비운 채 진행할 수 있는지.** 예를 들어 ⑧ 정답 라벨을 켜고 구축 방법만 고른 채 신뢰성을 비워 두는 경우다. 결정: 비운 채로는 진행할 수 없다. 켠 카드의 표준 보고 필드는 반드시 입력해야 하고, 모르면 "모름"을 골라야 한다. "모름"은 성적서에 "제공되지 않음"으로 찍힌다. 카드를 끄는 것은 여전히 허용된다.

## 구현 메모

**재료 레지스트리를 먼저 만든다.** 재료 목록 문서를 코드가 읽는 설정 파일 하나로 옮긴 것으로, 항목마다 소속 카드, 입력 방식, 구분, 적용 유형, 성적서 위치, AI 전달 여부를 담는다. 구성 화면의 카드, 하단 요약, 입력 단계 생성, 재료 선택 점검, 성적서 렌더링이 모두 이 파일 하나를 읽는다. 단계 목록도 고정 번호(현재 `STEP` 상수)가 아니라 선택 결과에서 계산한다.

현재 구현과 달라지는 점은 다음과 같다(재료 목록의 구현 상태 기준).

| 항목 | 현재 | 바꿀 것 |
| --- | --- | --- |
| ⑤ 평가 관점 전체 | 설계만 | 새로 만든다 |
| ⑦ 테스트 데이터 전체 | 설계만 | 새로 만든다 (데이터 출처는 재료 목록대로 한 줄 텍스트) |
| ⑧ 정답 라벨 전체 | 설계만 | 새로 만든다 |
| ⑥ 수집 환경 차이, 불균형 보정 | 설계만 | 새로 만든다. 수집 환경 차이는 복수 선택 + 기타 직접 입력 |
| ⑥ 수집 기간, 전처리 여부 | 재료 목록에 없음 (이번에 새로 추가) | 재료 목록 문서에 추가하고 새로 만든다. 전처리 여부는 직접 입력 |
| ⑨ 하이퍼파라미터, GPU 사용 여부 | 설계만 | 새로 만든다 |
| ⑥ 데이터 이름·데이터 양 | 필수 입력, AI에 안 감 | 선택 카드 안의 필드로 바꾸고 AI에 넘긴다 |
| ⑥ 클래스별 데이터 양 | 자유서술 | 클래스마다 숫자로 받는다 |
| ⑥ 검증 데이터 양 | 평가 표본 수 칸에도 인쇄되는 버그 | 버그를 고친다 |
| ⑨ 실행 환경 | AI에 안 가고 빠져도 경고 없음 | AI에 넘기고 빠지면 "제공되지 않음"으로 표시한다 |
| ④ 모델 이름·버전, 모델 용도 | AI에 안 감 | AI에 넘긴다 |
| ① 결과 파일 예시, ② 지표 목록 보기 | 없음 | 분류 유형별 버튼으로 새로 만든다 |
