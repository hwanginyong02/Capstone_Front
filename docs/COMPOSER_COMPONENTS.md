# 평가 흐름 항목(카드·필드) 목록

평가 흐름에 넣을 수 있는 블록(코드 이름은 카드) 9개와 그 안의 항목(필드)을 정리한 문서다. 코드의 정본은 재료 레지스트리(`src/data/reportComposer.ts`)이고, 이 문서는 그 내용을 사람이 읽기 쉽게 옮긴 것이다. 화면 배치와 흐름 규칙은 `docs/MATERIAL_PICKER.md` §12 에 있다.

## 개요

흐름은 작업 유형 → 평가 흐름 만들기 → 입력 화면(사용자가 정한 블록 순서) → 검증 → 확인과 생성이다.

- **평가 흐름 만들기**(`/app/composer`): 빈 흐름도에서 시작해 왼쪽 트리의 항목을 단계(의뢰 정보 · 모델 · 데이터 · 평가 기준)에 넣는다. 항목을 넣으면 그 블록이 생기고, 블록과 단계를 끌어 입력 순서를 정한다. 필수 항목을 모두 넣어야 "다음"으로 간다.
- **입력 화면**: 넣은 블록의 화면이 그 순서대로 나온다. 넣은 항목만 입력 칸이 보인다.
- **검증과 확인과 생성**: 늘 맨 끝이다.

트리에서 항목 이름을 누르면 설명 팝업이 뜬다. 팝업은 네 가지를 보여 준다.

- **의미**: 이 항목이 무엇인지 한 문장
- **입력 형태**: 어떤 값을 받는지(칸이 나뉜 항목은 칸 표)
- **입력 예시**: 실제 값의 예 (예: `전문가 / 크라우드소싱 / …`)
- **표준 근거**: TS 4213·ISO/IEC 17025 조항(근거가 있는 항목만)

성적서 위치와 AI 전달 여부는 개발자용 정보라 화면에 보이지 않고, 레지스트리에만 둔다.

## 카드를 나눈 기준과 구분 규칙

카드와 필드는 세 가지 기준으로 나눴다.

- 성적서의 **절이나 표가 생기고 사라지면 카드**, 같은 칸의 **내용만 바뀌면 필드**로 둔다.
- 업로드 파일 안의 컬럼(확률 점수, 응답시간 등)은 따로 줄 수 없으므로 **평가 데이터 카드에서 파일로 받고**, 컬럼 매핑 단계에서 확인한다.
- 기본값이 있거나 있으면 좋은 정도의 항목은 **더보기**로 접어 카드에 보이는 필드를 줄인다.

구분은 네 가지다(`docs/MATERIAL_PICKER.md` §6·§12.1, 코드 `PickKind`).

| 구분 | 뜻 | 넣지 않거나 비우면 |
| --- | --- | --- |
| 필수 | 성적서가 성립하는 데 꼭 필요한 값 (재료 선택 점검 1층) | 평가 흐름 만들기에서 넣지 않으면 "다음"으로 갈 수 없다. 입력 화면에서도 비운 채 진행할 수 없다 |
| 권장 | TS 4213 이 성적서에 적으라고 요구하는 표준 보고 항목 (재료 선택 점검 2층). 선택 블록의 필수 필드와 ① 지연시간 컬럼이다 | 넣지 않으면 성적서에 "제공되지 않음"으로 찍히고 하단 바와 검증 화면이 알린다. 넣었으면 비울 수 없고, 모르면 "모름"을 고른다("모름"도 "제공되지 않음"으로 센다) |
| 선택 | 성적서를 풍부하게 하는 값 | 그 칸이 빠진다 |
| 조건부 | 조건을 정하는 항목을 넣으면 함께 들어간다(따로 넣지 않고 개수에 세지 않는다). 조건이 성립하면 필수 | 조건에 따라 다르다 |

선택 블록(⑥~⑨)을 통째로 넣으면 그 블록의 권장 항목이 모두 들어간다. 항목 수와 구분 판정은 `flowStatus` 한 곳이 정한다(`docs/MATERIAL_PICKER.md` §12.2).

선택지에서 "모름"을 고르면 "제공되지 않음"으로 센다. 단, 수집 환경 차이(채널 효과)의 "알려진 것 없음"은 원문이 요구하는 답이라 제공된 것으로 센다. 작업 유형에 원래 없는 항목은 카드에서 숨기고 성적서에는 "해당 없음"으로 적는다.

### 덧붙이는 글 (서술 설계 D26, 점검 표 2.0)

서술 설계 결정 번호(D19·D26·D42·D44 등)의 뜻은 백엔드 저장소 `docs/ARCHITECTURE.md` §10 에 있다.

선택지로 답하는 서술 칸에는 선택지 아래에 **덧붙이는 글** 칸(500자)이 있다. 선택지가 사정을 다 담지 못할 때 의뢰자가 한두 줄을 덧붙이는 자리다. 글을 받는 서술 칸은 11개다.

| 카드 | 칸 | 층 |
| --- | --- | --- |
| ② 지표와 합격 기준 | 지표 선택 이유 (멀티레이블만 — 지표 화면 격자 아래) | 2층 |
| ⑤ 평가 관점 | 중요 오류 유형 (이진) · 클래스 중요도 (다중·멀티) · 사용 방식 | 1층 선언 |
| ⑥ 학습 데이터 | 수집 방식 차이(채널 효과) · 편향 감소 노력 | 2층 |
| ⑦ 테스트 데이터 | 학습 데이터와 출처 관계 | 2층 |
| ⑧ 정답 라벨 | 라벨 작성 주체 · 정답 라벨 신뢰성 · 일치도 종류 (복수 라벨러 합의일 때만) | 2층 |
| ⑨ 모델 설정과 실행 환경 | GPU 사용 여부 (학습·추론 두 줄 아래 한 칸) | 2층 |

서술 칸이 아닌 성적서 용도(③)와 학습과 같은 전처리(⑥)도 종전부터 같은 글 칸이 있다. 그래서 코드(`src/data/reportComposer.ts`)에서 글 칸(`allowsNote`)은 모두 13개이고, 그중 선택지가 필수인 칸(`noteNeedsChoice`)은 ⑤ 의 세 칸과 GPU 사용 여부, 네 개다.

글을 어떻게 세는지는 다음 규칙 하나로 정한다. 진행 점검(다음 버튼), 성적서 인쇄, 재료 선택 점검 2층 셈, AI 에 보내는 의뢰자 입력이 모두 이 규칙을 따른다(`src/lib/report/noteCountingRules.test.ts` 가 표로 고정한다).

- **1층 선언은 선택지가 필수다.** 글만 적고 선택지를 고르지 않으면 답이 아니다. 그래서 ⑤ 의 글 칸 안내는 "덧붙이는 글 (선택 — 위에서 하나를 고르세요)"이다.
- **2층은 글만 적어도 제공으로 센다.** 성적서에는 "의뢰자 제공: …"으로 찍힌다.
- **"모름" + 글은 제공이 아니다.** 그 보고 항목은 "제공되지 않음"으로 세지만, 글은 버리지 않고 성적서에 "제공되지 않음 (의뢰자 제공: …)"으로 찍고 AI 에도 보낸다.
- **"기타"를 고르고 내용을 비우면 제공이 아니다.**
- **GPU 사용 여부는 두 줄(학습·추론) 모두 선택이 필수다.** 글은 두 줄 아래 한 칸이고, 글만으로는 답이 되지 않는다.
- 선택값으로 판단하는 문장(정답 라벨 주의, 8.2 출처 관계 문장, 평가 관점 선언 등)은 고른 선택지만 읽는다. 글은 그 판단을 바꾸지 않는다.

이 규칙과 칸 이름 변경(불균형 보정 → 편향 감소 노력)이 들어간 것이 점검 표 2.0 이다. 점검 표 1.0 으로 만든 진행 중인 평가는 검증 화면과 성적서 화면에 "다시 확인" 안내가 뜬다.

## 카드 9개 한눈에 보기

필수 블록 5개(①~⑤)는 늘 입력 화면이 나오고, 그 안의 필수 항목을 모두 넣어야 "다음"으로 간다. 선택 블록 4개(⑥~⑨)는 항목을 하나라도 넣었을 때만 들어간다. 넣지 않은 선택 블록의 표준 보고 항목은 성적서에 "제공되지 않음"으로 찍힌다. 블록은 단계 4개(의뢰 정보 · 모델 · 데이터 · 평가 기준)로 묶인다(`docs/MATERIAL_PICKER.md` §2).

| 카드 | 구분 | 설명 | 적용 유형 |
| --- | --- | --- | --- |
| ① 평가 데이터 | 필수 | 예측 결과 파일 올리기 | 전부 |
| ② 지표와 합격 기준 | 필수 | 평가 지표와 목표 기준 | 전부 |
| ③ 의뢰자 정보 | 필수 | 성적서를 받는 회사와 용도 | 전부 |
| ④ 평가 대상 모델 | 필수 | 모델 이름과 쓰임새 | 전부 |
| ⑤ 평가 관점 | 필수 | 이 모델에서 무엇을 중요하게 볼지 | 전부 (필드는 유형별로 다름) |
| ⑥ 학습 데이터 | 선택 | 모델을 훈련할 때 쓴 데이터 | 전부 |
| ⑦ 테스트 데이터 | 선택 | 성능을 잰 테스트 데이터의 출처 | 전부 |
| ⑧ 정답 라벨 | 선택 | 테스트 데이터의 정답을 누가, 어떻게 붙였는지 | 전부 |
| ⑨ 모델 설정과 실행 환경 | 선택 | 모델 설정값과 실행한 컴퓨터 | 전부 |

사용자가 입력하는 항목은 모두 이 9개 블록 중 하나에 들어간다. 시스템이 계산하는 값은 사용자가 입력하지 않으므로 블록이 없고, 성적서 관리 항목(발급 확인, 정정 사유, 워크스페이스)은 성적서 내용이 아니라서 발급 단계에 둔다.

## 카드별 상세

각 카드는 설명 한 줄과 필드 표로 구성된다. 필드 이름은 명사로 쓰고, 뜻이 덜 전해지는 필드는 입력 화면에서 한 줄 도움말을 붙인다. 선택 카드(⑥\~⑨) 표의 "필수"는 화면에서 **권장**으로 보인다 — 넣은 항목만 입력 화면에서 비울 수 없고, 모르면 "모름"을 고른다.

### ① 평가 데이터 (필수)

예측 결과 파일 올리기.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 결과 파일 | `predictions.csv` 업로드 (CSV·JSON, 20 MiB 이하) | 필수 |
| 정답 컬럼 | `y_true` (매핑 화면에서 확인) | 필수 |
| 예측 컬럼 | `y_pred`, 또는 확률 컬럼(이진 `score`, 다중 `prob_<클래스>`, 다중 레이블 `score_<레이블>`) | 필수 |
| 양성 클래스 | 정답 값 중 하나 (`1`, `churn` …). 기본값은 백엔드가 정하고, 못 정하면 "정렬 순서상 뒤 값을 임시로 골랐습니다" 경고 | 필수 (이진) |
| 결정 임계값 | `0.5` (비우면 0.5) | 예측 없이 확률만 매핑했을 때 (이진·다중 레이블) |
| 지연시간 컬럼 | `latency_ms` (밀리초) | 권장 — 평가 흐름에 놓았을 때만 매핑 선택지에 있다 |
| 샘플 ID 컬럼 | `sample_id` | 선택 — 놓았을 때만 매핑 선택지에 있다 |
| 클래스 레이블 설명 | `cat = 집고양이 사진` (클래스마다 한 줄) | 선택 — 위와 같다 |

*(2026-10-19 갱신)* 매핑 항목은 평가 흐름에 놓지 않으면 받지 않는다(MATERIAL_PICKER.md §12.4). 확률 컬럼 이름은 접두어(`prob_`·`probability_`·`score_`·`p_`) 뒤에 데이터의 클래스·레이블 이름을 그대로 붙인다 — 예측 컬럼 없이 확률만 매핑하면 이 이름으로 클래스를 찾으므로, 맞지 않으면 검증 화면이 "확률 컬럼 이름" 오류로 막는다(업로드·매핑 화면이 미리 안내, MATERIAL_PICKER.md §12.7).

선택한 분류 유형의 예시 파일은 업로드 화면의 "파일 예시"와 평가 흐름 만들기의 결과 파일 설명 팝업이 같은 표로 보여 준다(`src/data/templateExamples.ts`). 컬럼 매핑, 양성 클래스, 결정 임계값은 컬럼 매핑 화면에서 받는다.

이진: 정답은 필수, 예측과 양성 확률(score) 중 하나는 필수. 확률이 있어야 AUROC 같은 곡선 지표를 쓸 수 있다. latency\_ms는 선택.

```csv
id,y_true,y_pred,score,latency_ms
S001,1,1,0.91,12
S002,0,1,0.62,9
S003,0,0,0.08,11
```

다중 클래스: 정답은 필수, 예측과 클래스별 확률(prob\_클래스명) 중 하나는 필수. 확률만 있으면 가장 높은 클래스를 예측으로 쓴다.

```csv
id,y_true,y_pred,prob_cat,prob_dog,prob_bird
S001,cat,cat,0.81,0.12,0.07
S002,dog,bird,0.10,0.35,0.55
S003,bird,bird,0.05,0.15,0.80
```

멀티레이블: 레이블은 | 로 구분하고, 빈칸은 레이블 없음이다. 정답은 필수, 예측과 레이블별 점수(score\_레이블명) 중 하나는 필수.

```csv
id,true_labels,pred_labels,score_sports,score_news
S001,sports|news,sports,0.92,0.41
S002,news,news,0.08,0.88
S003,,news,0.12,0.57
```

### ② 지표와 합격 기준 (필수)

평가 지표와 목표 기준.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 지표 | 선택한 분류 유형에서 고를 수 있는 지표 중 선택 (최소 1개) | 필수 |
| 합격 기준 | `Accuracy ≥ 0.85` (혼동행렬은 면제) | 필수 |
| β | `1.0` | Fβ 선택 시 |
| 지표 선택 이유 | `오차를 고르게 봄 / 모든 레이블 일치 / 겹치는 정도 / 기타(직접 입력)` | 필수 (멀티레이블만) |
| 핵심 지표 | `Accuracy · F1` (유형별 기본값을 미리 체크) | 필수 (최소 1개) |

핵심 지표는 지표와 합격 기준 화면(`/app/metrics`, `pages/TestItems.tsx`)의 합격 기준 표에서 목표값 옆 체크칸으로 고른다. 판정이 목표값과 함께 정해지기 때문이다. 유형별 기본값(이진·다중 클래스 Accuracy·F1, 멀티레이블 F1·Jaccard)이 미리 체크돼 있다. 핵심 지표가 목표에 미달하면 최종 불합격이고, 그 밖의 지표가 미달하면 조건부 합격이고, 핵심 지표가 산출되지 않았거나 판정 대상이 없으면 판정 불가다(서술 설계 D19). 목표값이 있는 지표가 있으면 최소 1개를 골라야 넘어갈 수 있다. 성적서 시험 결과 표에는 핵심 지표에 "핵심" 표시가 붙고, 6.1 표 아래에 판정 규칙(고정 문구 10)이 찍힌다.

| 분류 유형 | 고를 수 있는 지표 |
| --- | --- |
| 이진 (15개) | M1 Accuracy, M2 Precision, M3 Recall, M4 F1, M5 Fβ, M6 KL Divergence, M7 Specificity, M8 FPR, M9 AUROC\*, M10 AUPRC\*, M19 Log Loss\*, M20 MCC, M21 혼동행렬, M22 클래스별 지표, M23 불균형 비율 |
| 다중 클래스 (13개) | M1 Accuracy, M2 Precision, M3 Recall, M4 F1, M5 Fβ, M6 KL Divergence, M11 Macro 평균, M12 Micro 평균, M13 Weighted 평균, M14 분포 차이, M21 혼동행렬, M22 클래스별 지표, M23 불균형 비율 |
| 멀티레이블 (11개) | M2 Precision, M3 Recall, M4 F1, M5 Fβ, M15 Hamming Loss, M16 Exact Match, M17 Jaccard, M18 분포 차이, M21 혼동행렬, M22 레이블별 지표, M23 불균형 비율 |

\* 확률(score) 컬럼이 있어야 고를 수 있다. 확률 컬럼을 매핑하지 않았으면 지표 화면에서 이유와 함께 비활성으로 보인다(MATERIAL_PICKER.md §3).

멀티레이블에서는 M1 Accuracy를 고를 수 없다. TS 4213 6.5.1은 멀티레이블에서 정확한 일치율을 "이진 정확도를 조정한 것"으로, 6.5.3은 이를 "서브 세트 정확도"로 정의하므로 멀티레이블의 Accuracy는 M16 Exact Match와 같은 값이다. 백엔드도 같은 이유로 멀티레이블에서 M1·M11·M12·M13을 노출하지 않는다(app/core/schemas.py, 2026-09-07 결정 2).

### ⑤ 평가 관점 (필수)

이 모델에서 무엇을 중요하게 볼지. 필드는 분류 유형에 따라 다르며, 사용자는 항상 두 개를 받는다.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 중요 오류 유형 | `놓침(FN) / 잘못 잡음(FP) / 비슷함` | 필수 (이진) |
| 클래스 중요도 | `모두 동등 / 큰 클래스 우선 / 개별 샘플 우선` | 필수 (다중·멀티) |
| 사용 방식 | `실시간 응답 / 일괄 처리` | 필수 |

고른 지표가 답과 맞지 않으면 지표 화면의 "목적별 점검"과 검증 화면의 생성 전 안내에서 경고한다(진행은 막지 않는다). 판정은 재료 선택 점검 함수 하나(`src/lib/report/materialCheck.ts`, 점검 표 2.0)가 한다. 값은 성적서 5절에 인쇄되고 AI 서술의 기준이 된다.

| 필드 | 선택지 | 확인하는 것 | 근거 (TS 4213) |
| --- | --- | --- | --- |
| 중요 오류 유형 | 놓침(FN) | Recall 또는 β가 1보다 큰 Fβ를 골랐는가 | 6.2.6 |
| 중요 오류 유형 | 잘못 잡음(FP) | Precision 또는 β가 1보다 작은 Fβ를 골랐는가 | 6.2.6 |
| 중요 오류 유형 | 비슷함 | 확인 없음 | 6.2.6 |
| 클래스 중요도 | 모두 동등 | 매크로 평균 지표를 골랐는가 | 6.4.3 |
| 클래스 중요도 | 큰 클래스 우선 | 가중 평균 지표를 골랐는가 | 6.4.3 |
| 클래스 중요도 | 개별 샘플 우선 | 마이크로 평균 지표를 골랐는가 | 6.4.3 |
| 사용 방식 | 실시간 응답 | 지연시간(latency) 컬럼을 매핑했는가 | 6.6.2 |
| 사용 방식 | 일괄 처리 | 확인 없음 | 6.6.2 |

다중 클래스의 Accuracy는 마이크로 평균 지표로 인정하고, 클래스별 지표(M22)를 고르면 세 평균 방식이 모두 있는 것으로 본다. 멀티레이블은 모두 동등이면 Precision·Recall·F1·Fβ·M22, 나머지 둘은 M22만 인정한다. 위 표 밖에 한 줄이 더 있다: 이진에서 곡선 지표(AUROC·AUPRC)를 골랐고 불균형 비율이 9를 넘으면 AUPRC가 있어야 한다(6.3.6·6.3.7).

### ⑥ 학습 데이터 (선택)

모델을 훈련할 때 쓴 데이터.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 데이터 이름 | `고객 로그 2024` | 필수 |
| 데이터 출처 | `사내 CRM 로그` (한 줄) | 필수 |
| 데이터 양 | `학습 12,000건 · 검증 3,000건` (칸마다 "모름" 가능) | 필수 |
| 클래스별 데이터 양 | `정상 8,400 / 이탈 3,600` (평가 데이터의 클래스마다 한 칸 — **모두** 채우거나 "모름") | 필수 |
| 수집 방식 차이(채널 효과) | `☐ 알려진 것 없음 ☐ 수집 장치 차이 ☐ 전처리 차이 ☐ 수집자 차이 ☐ 수집 환경 차이 ☐ 기타(직접 입력)` (복수 선택) | 필수 |
| 편향 감소 노력 | `☐ 클래스 수 맞춤 ☐ 출처 다양화 ☐ 보정 안 함 ☐ 기타(직접 입력)` (복수 선택, 모름 가능) | 필수 |
| 학습 데이터 설명 | `2024년 고객 로그에서 이탈 여부를 붙인 것` (직접 입력) | 선택 |
| 수집 기간 | 시작 월 `2023-01` · 끝 월 `2024-12` | 선택 (더보기) |
| 데이터 형식 | `CSV, 이미지(JPG/PNG)` | 선택 (더보기) |
| 비고 | `이상치가 있던 이틀은 뺐다` (직접 입력) | 선택 (더보기) |
| 학습과 같은 전처리 | `같음 / 다름 / 모름` + 덧붙이는 글 (⑦ 에서 옮김) | 선택 |
| 적합 예시 파일 | `normal_01.png, sample.csv` (이미지·CSV·JSON, 여러 개) | 선택 |
| 부적합 예시 파일 | `blurry_03.png` | 선택 |

적합·부적합 예시 파일은 카드 폼 아래에서 따로 받는다(레지스트리에는 학습 데이터 화면이 받는 항목으로 있다). 이미지·CSV·JSON 만 받고, 형식(MIME)이 비어 오는 파일(일부 브라우저의 HEIC 등)은 확장자로 본다(MATERIAL_PICKER.md §12.5·§12.7).

도움말: 수집 방식 차이는 "같은 클래스의 데이터가 서로 다른 장비, 처리 방식, 사람, 환경에서 모였는지"(TS 4213 5.3.8 채널 효과)를 묻는다. 차이가 여러 개일 수 있어 복수 선택이고, "알려진 것 없음"은 다른 선택지와 함께 고를 수 없으며 제공된 것으로 센다. 편향 감소 노력은 "한쪽 클래스에 몰린 데이터를 어떻게 다뤘는지"(TS 4213 8절 보고 항목 이름 그대로 — 화면 이름은 예전에 "불균형 보정"이었다)를 묻는다. 여러 노력을 함께 했을 수 있어 복수 선택이고, "보정 안 함"은 다른 선택지와 함께 고를 수 없다. 두 필드 모두 "기타"를 고르면 내용을 적을 칸이 나타나고, 비워 두면 진행할 수 없다.

이 카드가 학습 데이터의 유일한 입력처다. 종전에는 Details 화면의 학습 데이터셋 폼이 이름·건수·클래스 분포·형식을 따로 받았고 성적서는 그쪽만 읽었다. 폼을 이 카드로 합쳤다(persist v10). 이 블록을 넣지 않으면 성적서 학습 데이터 표의 2층 항목이 "제공되지 않음"으로 찍힌다.

학습 데이터 설명·비고는 성적서 학습 데이터 절에 인쇄된다. 종전에는 Details 의 "Report notes"(평가에 대한 메모)가 이 자리에 "학습 데이터 설명"으로 찍혔다. 그 칸은 없앴다. 전처리 자유서술 칸은 없애고 ⑦ 의 "학습과 같은 전처리" 한 칸으로 바꿨다(서술 설계 D44 — 지금은 이 카드에 있다).

### ⑧ 정답 라벨 (선택)

테스트 데이터의 정답을 누가, 어떻게 붙였는지.

| 필드 | 입력 예시 | 구분 |
| --- | --- | --- |
| 라벨 작성 주체 | `전문가 / 크라우드소싱(외부 작업자) / 프로그램·규칙 / 실제 결과 기록 / 기타(직접 입력)` | 필수 |
| 정답 라벨 신뢰성 | `복수 라벨러 합의 / 단일 라벨러 / 검토 없음 / 모름` | 필수 |
| 라벨러 수 | `3` (2 이상의 정수) | 복수 라벨러 합의일 때 |
| 일치도 종류 | `단순 일치율 / Cohen의 카파 / Fleiss의 카파 / Krippendorff의 알파 / 기타(이름 직접 입력) / 측정 안 함` | 복수 라벨러 합의일 때 |

도움말: 정답이 틀리면 점수도 믿을 수 없어서 정답의 출처를 성적서에 적는다. 실제 결과 기록은 "실제 해지 여부"처럼 사후에 확인된 결과를 정답으로 쓴 경우다.

수집 기간은 시작 월과 끝 월 두 칸이다(⑥ ⑦ 공통). 한쪽만 적었거나 시작이 끝보다 늦으면 진행할 수 없다. 라벨러 수·일치도 값도 범위를 벗어나면 진행할 수 없고, 일치도 값의 범위는 고른 종류를 따른다. 라벨러가 2명이면 Fleiss의 카파를, 3명 이상이면 Cohen의 카파를 고를 수 없다(서술 설계 D42). 이런 틀린 값은 다음을 누르기 전부터 표시한다. "측정 안 함"은 제공된 답으로 센다.

## 평가 관점 질문의 원칙

평가 관점은 사용자가 선택지로 답하는 **고정 질문**이다. AI가 만드는 질문이 아니고, 모델마다 달라지지도 않는다. 분류 유형에 따라서만 달라진다.

질문은 늘어날 수 있지만, 새 질문은 두 가지를 갖춰야 한다. TS 4213의 근거 조항이 있어야 하고, 그 답이 요구하는 재료(점검 줄, 예: "대화형이면 지연시간 필요")가 정해져야 한다. 점검에 쓰이지 않는 질문은 평가 관점이 아니라 일반 입력 필드다.
